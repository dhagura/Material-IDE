Unidad 3 — Publicación de servicios interoperables y APIs geoespaciales

1. Marco de la semana

La Semana 12 trabaja coberturas y teselas: WCS, WMTS, OGC API - Tiles, OGC API - Coverages u opciones equivalentes según el producto. También aborda estilos, generalización, caché, teselado y rendimiento.

El objetivo es mostrar que la arquitectura de publicación debe adaptarse al tipo de recurso y patrón de uso. No todos los datos deben entregarse como WMS o features.

2. Propósito

Un ráster científico, una ortofoto, un mapa base y una capa vectorial altamente demandada tienen necesidades diferentes. Publicar todo mediante renderizado dinámico puede producir costos innecesarios.

La semana introduce mecanismos especializados para coberturas y para mapas teselados, junto con técnicas de rendimiento que permiten reducir carga sin sacrificar interoperabilidad.

3. Resultados de aprendizaje

El estudiante deberá distinguir cobertura, mapa dinámico y tesela; explicar WCS y WMTS; comprender el propósito de OGC API - Tiles y Coverages; configurar o probar caché; analizar niveles de zoom, generalización y rendimiento; y elegir el mecanismo apropiado según el producto.

4. ¿Qué es una cobertura?

Una cobertura representa valores asociados a posiciones dentro de un dominio espacial, temporal u otro. Los rásteres son una forma común, pero el concepto es más general.

Ejemplos:

  • Modelo digital de elevación;
  • Temperatura;
  • Precipitación;
  • Imagen multiespectral;
  • Concentración de contaminantes.

A diferencia de un WMS, que entrega una representación visual, un servicio de coberturas puede entregar valores de datos para análisis.

5. WCS

Web Coverage Service (WCS) permite acceder a coberturas y subconjuntos manteniendo valores originales para procesamiento [R1].

La diferencia conceptual es importante:

WMS → mapa renderizado
WCS → valores de cobertura

Un científico que necesita elevaciones numéricas requiere algo distinto de un usuario que solo necesita visualizar relieve.

6. Subsetting

Las coberturas pueden ser muy grandes. Un servicio útil debería permitir solicitar una parte espacial, temporal o dimensional cuando la implementación lo soporte.

Esto reduce transferencia y procesamiento.

Ejemplo

En lugar de descargar un modelo de elevación nacional completo, el usuario solicita un recorte para una cuenca determinada.

La interfaz debe documentar CRS, resolución, formato y dimensiones.

7. OGC API - Coverages

La familia OGC API extiende el enfoque web moderno hacia coberturas. Su objetivo es proporcionar interfaces basadas en recursos y bloques reutilizables para acceso a datos de cobertura [R4].

Durante la asignatura interesa comprender la evolución conceptual y revisar implementaciones disponibles, sin asumir que todas las plataformas soportan las mismas partes o extensiones.

8. ¿Qué es una tesela?

Una tesela divide una representación espacial en pequeñas piezas organizadas por niveles de zoom y posiciones.

flowchart TB
    Z0["Zoom 0: pocas teselas"] --> Z1["Zoom 1: más detalle"]
    Z1 --> Z2["Zoom 2: más teselas"]
    Z2 --> ZN["Zoom N: detalle local"]

El cliente solicita únicamente las teselas necesarias para la ventana visible. Esto permite reutilización y mejora tiempos de respuesta para mapas de alta demanda.

9. WMTS

Web Map Tile Service (WMTS) estandariza acceso a mapas teselados [R2]. A diferencia de WMS dinámico, las teselas se organizan en una matriz predefinida.

El servidor puede precalcular y almacenar resultados, reduciendo costo de renderizado repetitivo.

Ventaja

Excelente para mapas base o capas que cambian con poca frecuencia y reciben muchas solicitudes.

Limitación

Menor flexibilidad para combinaciones arbitrarias de BBOX, tamaño y estilos en cada petición.

10. WMS versus WMTS

Aspecto WMS WMTS
Imagen Renderizada por solicitud Teselas en matriz
Flexibilidad Alta Más estructurada
Caché Posible, pero adicional Parte natural del patrón
Uso típico Mapas dinámicos Mapas base y alta demanda
Estilos por petición Puede soportarse Normalmente predefinidos

La elección depende de frecuencia de cambio, demanda y necesidad de personalización.

11. OGC API - Tiles

OGC API - Tiles proporciona una aproximación web moderna para describir y acceder a recursos teselados [R3]. Puede relacionarse con conjuntos de matrices y otras APIs OGC.

La idea importante es la misma: permitir que el cliente descubra esquemas de teselado y solicite piezas de manera interoperable, pero utilizando patrones más alineados con APIs actuales.

12. Tile Matrix Set

Una matriz de teselas define niveles, extensión, resolución y organización de columnas/filas. Dos servicios pueden utilizar matrices distintas, por lo que el cliente necesita descubrir qué esquema está disponible.

En aplicaciones web, los esquemas globales asociados a mapas web son comunes, pero una IDE puede necesitar matrices específicas para otros CRS o escalas institucionales.

13. Caché

La caché almacena resultados de solicitudes para reutilizarlos.

flowchart LR
    C["Cliente"] --> K{"¿Existe en caché?"}
    K -- "Sí" --> R["Respuesta rápida"]
    K -- "No" --> S["Servidor renderiza"]
    S --> K

La caché puede existir en servidor, proxy, CDN, navegador o varias capas.

El desafío principal es la invalidación: cuando el dato cambia, las respuestas antiguas no deben mantenerse indefinidamente.

14. Invalidación de caché

La organización debe definir qué ocurre cuando se actualiza una capa.

Alternativas:

  • Vaciar todas las teselas;
  • Invalidar solo el área afectada;
  • Utilizar versiones de capa;
  • Definir expiración temporal.

La estrategia depende de tamaño, frecuencia de cambio y criticidad de la vigencia.

Ejemplo

Un mapa base que cambia trimestralmente puede precalcularse. Una capa de incidentes en tiempo real necesita otra estrategia y probablemente no debe depender de una caché de larga duración.

15. Generalización

La generalización adapta geometrías y contenido al nivel de escala. No tiene sentido enviar millones de vértices cuando el usuario visualiza un país completo.

Técnicas posibles incluyen simplificación, agregación, selección de objetos y cambio de representación.

La generalización debe preservar significado y evitar distorsiones importantes. También puede mejorar rendimiento de WMS, vector tiles o APIs.

16. Pirámides y overviews ráster

Los rásteres grandes pueden almacenar representaciones de menor resolución para distintos niveles de zoom. Esto evita leer el dataset completo para generar una vista reducida.

Herramientas de bases ráster, GDAL y servidores pueden aprovechar estas pirámides.

La preparación del dato y la publicación deben diseñarse conjuntamente.

17. Rendimiento extremo a extremo

El rendimiento de una IDE no depende de un único servidor.

flowchart LR
    C["Cliente"] --> N["Red"]
    N --> S["Servicio"]
    S --> D["Base / archivo"]
    S --> K["Caché"]

Puede existir demora en red, renderizado, consulta, reproyección, lectura de disco o cliente.

Medir solo CPU del servidor no permite conocer toda la experiencia.

18. Métricas de rendimiento

Pueden observarse:

  • Tiempo total de respuesta;
  • Tamaño transferido;
  • Solicitudes por segundo;
  • Tasa de aciertos de caché;
  • Uso de CPU/memoria;
  • Tiempo de consulta a base;
  • Errores y timeouts.

Las métricas deben relacionarse con casos de uso reales. Una prueba con un único usuario no representa necesariamente una aplicación pública concurrida.

19. Carga y pruebas

Una prueba de carga genera solicitudes controladas para observar comportamiento.

El objetivo docente no es realizar ingeniería de performance avanzada, sino comparar escenarios:

  • WMS sin caché;
  • WMS con caché;
  • Geometría completa versus generalizada;
  • Ráster sin overviews versus con overviews.

Las conclusiones deben basarse en medidas.

20. Estilos y rendimiento

La simbología puede afectar notablemente el costo de renderizado. Etiquetas, reglas complejas, transparencias y filtros pueden aumentar tiempo.

La optimización no debería eliminar información necesaria. Se debe buscar equilibrio entre legibilidad, precisión y costo.

Ejemplo

Puede ser mejor utilizar una capa agregada a escalas pequeñas y cambiar a objetos detallados al acercarse.

21. Caso integrador

El proyecto dispone de una ortofoto y una capa de calles.

  • La ortofoto se prepara con overviews y puede servirse mediante teselas para visualización.
  • Las calles se generalizan para escalas pequeñas y utilizan estilos por jerarquía.
  • Las capas de alta demanda se cachean.
  • La fuente detallada permanece disponible para análisis autorizado.

El catálogo relaciona cada producto con su propósito y resolución.

Casos técnicos guiados — Teselas, coberturas y rendimiento

La elección entre WMS, teselas y coberturas depende del tipo de dato y del uso. Esta sección desarrolla ejemplos concretos para evitar tratarlos como nombres de estándares aislados.

Ejemplo 1 — ¿Cuándo usar WMS y cuándo teselas?

Supongamos un mapa base municipal que casi no cambia y es consultado por miles de usuarios. Renderizar cada vista mediante WMS puede repetir el mismo trabajo. Un esquema de teselas permite precalcular o almacenar respuestas reutilizables.

En cambio, una capa que cambia a cada minuto o que necesita estilos personalizados por solicitud puede beneficiarse menos de un caché agresivo.

Ejemplo 2 — Estructura de una tesela

Una tesela se identifica normalmente mediante un conjunto de coordenadas discretas dentro de una matriz. Conceptualmente:

z = nivel de zoom
x = columna
y = fila

En APIs modernas, OGC API - Tiles define rutas basadas en colecciones, tilesets y Tile Matrix Sets. Una ruta conceptual es:

/collections/{collectionId}/tiles/{tileMatrixSetId}/{tileMatrix}/{tileRow}/{tileCol}

El estudiante debe comprender que estas coordenadas no son longitud/latitud directa; identifican una celda dentro de una matriz de teselado.

Ejemplo 3 — Pirámide de teselas

flowchart TB
    Z0["Zoom 0<br/>muy pocas teselas"] --> Z1["Zoom 1<br/>más detalle"]
    Z1 --> Z2["Zoom 2"]
    Z2 --> ZN["Zoom n<br/>muchas teselas pequeñas"]

A mayor nivel de zoom aumenta el número de teselas. Por eso generar toda una pirámide para un territorio enorme puede consumir mucho almacenamiento. Deben definirse extensión y niveles realmente necesarios.

Ejemplo 4 — Caché y clave de una respuesta

Para que un caché reutilice una tesela, la clave debe distinguir parámetros que cambian la imagen: capa, estilo, CRS, nivel, fila, columna y, cuando corresponda, dimensiones como fecha.

Si una capa temporal utiliza la misma clave para dos fechas diferentes, el usuario podría recibir una imagen antigua aunque el servidor de origen tenga datos nuevos.

Ejemplo 5 — Invalidación de caché

Supongamos que áreas verdes cambian cada trimestre. Después de actualizar la fuente:

  1. se valida la nueva versión;
  2. se publica;
  3. se invalidan las teselas afectadas;
  4. se regeneran bajo demanda o en un proceso programado;
  5. se verifica que el cliente ya no recibe imágenes antiguas.

Un caché que nunca se invalida puede mejorar rendimiento y empeorar vigencia.

Ejemplo 6 — WCS y coberturas

Un modelo digital de elevación no se representa naturalmente como una colección de polígonos. Es una cobertura donde cada posición tiene un valor.

Una petición de cobertura puede buscar un subconjunto espacial para análisis, en vez de solicitar solo una imagen renderizada.

Diferencia conceptual

WMS      → “Muéstrame cómo se ve esta cobertura”.
WCS/API  → “Entrégame los valores de esta cobertura para procesarlos”.

Ejemplo 7 — OGC API - Coverages

Una implementación moderna puede exponer una colección ráster mediante API. El estudiante debe revisar:

  • Dominios espacial y temporal. Permiten conocer qué territorio, alturas o periodos están realmente disponibles antes de solicitar datos.
  • Formato de salida. Determina cómo se entregarán valores y metadatos y qué herramientas podrán procesarlos.
  • Subconjuntos soportados. Indican si el servidor puede recortar por ejes o rangos para evitar transferir la cobertura completa.
  • CRS. Debe verificarse tanto el sistema del dominio como las capacidades de transformación anunciadas por la implementación.
  • Tamaño de respuesta. Una cobertura puede ser varios órdenes de magnitud mayor que una imagen WMS; el cliente debe solicitar únicamente la región necesaria.

No todos los servidores implementan las mismas extensiones; por ello debe leerse la declaración de conformidad de la implementación elegida.

Ejemplo 8 — Generalización vectorial

Una red vial con millones de vértices puede ser necesaria para análisis detallado, pero excesiva para una vista regional.

Una estrategia es crear productos por escala:

1:5.000    → geometría detallada
1:25.000   → simplificación moderada
1:100.000  → ejes principales

En PostGIS, ST_Simplify puede utilizarse para experimentar, pero la tolerancia debe revisarse porque puede alterar topología o significado.

Ejemplo 9 — Medición comparativa

Realizar tres pruebas sobre la misma extensión:

Prueba Respuesta Tamaño Tiempo
WMS sin caché PNG registrar registrar
WMS repetido / caché PNG registrar registrar
Tesela PNG/WebP registrar registrar

El objetivo es medir, no asumir que el caché “siempre es más rápido”.

Ejemplo 10 — Diagnóstico de un mapa lento

Orden sugerido:

  1. medir tiempo total;
  2. revisar tamaño de imagen;
  3. revisar cantidad de features renderizados;
  4. comprobar índices espaciales;
  5. evaluar complejidad de estilo;
  6. revisar reproyección en tiempo real;
  7. observar logs y CPU;
  8. probar generalización o caché;
  9. repetir medición.

Ejercicio integrador

Para una capa vectorial y una cobertura, justificar qué interfaz se utilizaría para: visualización, análisis detallado, mapa base y descarga. La respuesta debe basarse en necesidad y rendimiento, no en preferencia por una tecnología.

Referencia técnica: OGC API - Tiles Part 1 Core describe los recursos de tiles y Tile Matrix Sets; el programa incorpora WCS, WMTS, OGC API Tiles y OGC API Coverages como alternativas de publicación según el producto.

25. Preguntas de cierre

¿Por qué WCS no es lo mismo que WMS?

WMS entrega una representación visual; WCS está orientado a valores de cobertura que pueden utilizarse analíticamente.

¿Cuándo conviene WMTS?

Cuando existe alta demanda de mapas relativamente estables y puede aprovecharse un esquema de teselas precalculadas o cacheadas.

¿Por qué la caché puede mostrar información antigua?

Porque reutiliza respuestas previas. La estrategia debe incluir invalidación o expiración coherente con la frecuencia de actualización.

26. Errores frecuentes

  • “Teselar siempre mejora cualquier capa”. Introduce rigidez y almacenamiento; debe responder al patrón de uso.
  • “Caché significa que el dato queda duplicado sin control”. Debe gestionarse como producto derivado con reglas de invalidación.
  • “Generalizar es simplemente reducir vértices”. También puede implicar selección, agregación y cambio de representación.

30. Síntesis

La Semana 12 muestra que la publicación debe adaptarse al tipo de información y demanda. Una IDE eficiente combina mapas dinámicos, objetos, coberturas, teselas, caché y generalización según el caso, en lugar de resolver todo mediante una única interfaz.
