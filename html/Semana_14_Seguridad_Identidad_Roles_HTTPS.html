1. Marco de la semana

La Semana 14 desarrolla identidad, autenticación, autorización, roles, permisos, HTTPS, gestión de credenciales, exposición de servicios y protección de datos. El programa exige que la IDE operativa incorpore controles de acceso y seguridad coherentes con el tipo de información y los usuarios.

La semana toma las decisiones de clasificación realizadas en Semana 3 y las convierte en controles técnicos verificables.

2. Propósito

La seguridad no consiste únicamente en “poner contraseña” a un servidor. Una IDE tiene múltiples superficies: base de datos, servicios, APIs, catálogo, aplicaciones, administración y redes. Cada componente necesita comprender quién accede, a qué recurso y con qué privilegios.

El objetivo de la semana es diseñar una cadena de confianza: identidad → autenticación → autorización → acción → registro.

3. Resultados de aprendizaje

Al finalizar la semana, el estudiante deberá distinguir identidad, autenticación y autorización; diseñar roles y permisos; aplicar mínimo privilegio; proteger comunicaciones con HTTPS; gestionar credenciales de manera segura; identificar superficies expuestas y demostrar acceso diferenciado entre perfiles.

También deberá reconocer que la seguridad debe combinar controles preventivos, detectivos y de recuperación.

4. Identidad

Una identidad representa a una persona, sistema o servicio dentro de la infraestructura. No todas las identidades son usuarios humanos.

Ejemplos:

  • Analista SIG;
  • Administrador;
  • Ciudadano autenticado;
  • Aplicación web;
  • Servicio de integración;
  • Cuenta de respaldo.

Separar identidades permite atribuir acciones y evitar credenciales compartidas difíciles de auditar.

5. Autenticación

La autenticación verifica que una identidad es quien afirma ser. Puede utilizar contraseñas, certificados, tokens, llaves u otros mecanismos.

La elección depende del tipo de cliente y riesgo. Una aplicación automatizada no debería autenticarse necesariamente igual que una persona.

Principio

Las credenciales deben pertenecer a identidades concretas y gestionarse institucionalmente. Compartir una única cuenta administrativa entre varias personas elimina trazabilidad.

6. Autorización

La autorización determina qué puede hacer una identidad ya autenticada.

Ejemplo:

Usuario A → Puede visualizar áreas verdes
Usuario B → Puede editar datos internos
Servicio público → Puede leer vista pública
Administrador → Puede configurar capas

La autorización debe derivarse de roles y políticas, no de permisos asignados de manera improvisada usuario por usuario.

7. Autenticación versus autorización

Un usuario puede autenticarse correctamente y seguir sin autorización para acceder a un recurso.

flowchart LR U["Identidad"] --> A["Autenticación"] A --> B{"¿Autenticado?"} B -- "No" --> X["Acceso rechazado"] B -- "Sí" --> C["Autorización"] C --> D{"¿Permiso?"} D -- "No" --> X D -- "Sí" --> R["Recurso"]

Esta separación es importante para interpretar códigos 401 y 403 y para diseñar sistemas de roles.

8. Roles

Un rol agrupa permisos asociados a una función.

Ejemplo didáctico:

Rol Capacidades principales
Público Consultar capas abiertas
Analista Consumir servicios internos
Productor Editar datasets asignados
Publicador Configurar servicios autorizados
Administrador Gestionar plataforma

Los roles deben corresponder a responsabilidades reales y mantenerse simples. Crear decenas de roles casi idénticos aumenta errores de administración.

9. Mínimo privilegio

El principio de mínimo privilegio indica que cada identidad debe recibir únicamente los permisos necesarios y durante el tiempo necesario.

Ejemplo

La cuenta usada por un visor público necesita leer una vista de publicación. No necesita crear tablas, editar usuarios ni acceder a campos internos.

Reducir privilegios disminuye el impacto de errores y compromisos de credenciales.

10. Matriz de acceso

La matriz de acceso traduce clasificación de datos en permisos.

Recurso Público Analista Productor Administrador
Áreas verdes públicas Leer Leer Editar fuente Administrar
Predios internos No Leer Editar Administrar
Configuración servidor No No No Administrar

Esta matriz debe coincidir con la gobernanza de Semana 2 y la política de Semana 3.

11. Seguridad en la base de datos

Los permisos de base deben separar lectura, escritura, administración y cuentas de servicio.

Medidas recomendadas:

  • Cuentas individuales o de servicio identificables;
  • Contraseñas o secretos gestionados fuera del código;
  • Privilegios mínimos;
  • Esquemas separados cuando sea útil;
  • Restricciones de red;
  • Auditoría de operaciones relevantes.

La aplicación pública no debería conectarse con una cuenta superusuario.

12. Seguridad en servicios geoespaciales

Los servidores de mapas y APIs deben proteger capas, endpoints y funciones administrativas.

No basta con ocultar una URL. Un endpoint “secreto” pero accesible públicamente sigue expuesto.

Prueba

Intentar acceder con un usuario autorizado, uno no autorizado y sin autenticación. Documentar diferencias y códigos de respuesta.

13. HTTPS y TLS

HTTPS protege la comunicación mediante TLS. Esto evita que credenciales y contenido viajen en texto claro por la red.

Los certificados deben:

  • Corresponder al dominio;
  • Estar vigentes;
  • Renovarse antes de expirar;
  • Utilizar una cadena de confianza apropiada;
  • Configurarse con versiones y cifrados aceptables.

RFC 8446 define TLS 1.3 [R2]. La configuración concreta depende de la plataforma y políticas institucionales.

14. Reverse proxy y terminación TLS

El reverse proxy de Semana 13 puede centralizar HTTPS para varios servicios internos.

flowchart LR U["Cliente HTTPS"] --> P["Reverse proxy TLS"] P --> G["GeoServer"] P --> A["API"] P --> C["Catálogo"]

Esto simplifica certificados, pero el tráfico interno también debe evaluarse según el riesgo. Además, el proxy no reemplaza autorización dentro de las aplicaciones.

15. Gestión de credenciales

Las credenciales no deberían almacenarse en:

  • Repositorios públicos;
  • Imágenes de contenedor;
  • Scripts compartidos;
  • Documentos de laboratorio;
  • URLs visibles.

La organización debe definir cómo crear, rotar, revocar y recuperar credenciales.

Rotación

Cambiar periódicamente o tras incidentes reduce exposición, pero debe realizarse sin interrumpir servicios. Las cuentas de servicio necesitan procesos especialmente controlados.

16. Tokens y APIs

Las APIs pueden utilizar tokens u otros mecanismos. El token representa autorización y debe protegerse igual que una contraseña cuando permite acceder a recursos.

No debe registrarse completo en logs ni enviarse por canales inseguros.

Los tokens pueden tener expiración y alcances limitados, reduciendo riesgo frente a credenciales permanentes.

17. Exposición de servicios

La arquitectura debe distinguir servicios públicos y administrativos.

flowchart TB INTERNET["Internet"] --> PUB["Servicios públicos"] ADMIN["Red/VPN administrativa"] --> ADM["Interfaces de administración"] PUB --> DBR["Cuenta lectura"] ADM --> DBW["Cuenta administración"]

La interfaz administrativa no debería estar expuesta únicamente porque comparte aplicación con un servicio público.

18. Segmentación

Separar redes o zonas limita movimiento lateral y reduce superficie expuesta.

Una topología puede distinguir:

  • Zona pública;
  • Servicios de aplicación;
  • Datos;
  • Administración.

La complejidad debe ser proporcional al entorno. En laboratorio puede representarse lógicamente mediante redes de contenedores y puertos no publicados.

19. Logs de seguridad

Los eventos relevantes deberían permitir detectar intentos fallidos, cambios administrativos y accesos anómalos.

El registro debe equilibrar trazabilidad con privacidad: no conviene almacenar contraseñas, tokens completos o datos sensibles innecesarios.

Semana 15 utilizará logs como fuente de monitoreo y diagnóstico.

20. Amenazas básicas en APIs y servicios

OWASP API Security Top 10 es una referencia complementaria útil para analizar riesgos de autorización, autenticación, consumo de recursos y configuración [R3].

La asignatura no busca realizar pentesting ofensivo, sino aprender a reconocer controles básicos:

  • Autorización por objeto y función;
  • Límites de solicitudes;
  • Validación de entrada;
  • Gestión de inventario de APIs;
  • Configuración segura.

21. Disponibilidad como parte de seguridad

La seguridad también incluye mantener capacidades disponibles. Una API sin límites puede agotarse por consultas demasiado grandes aun sin existir un ataque sofisticado.

Límites de registros, timeouts, caché y monitoreo ayudan a proteger recursos.

Esto conecta seguridad con rendimiento y continuidad.

22. Caso integrador

El proyecto define:

  • WMS de áreas verdes público;
  • WFS/API de predios restringido;
  • Catálogo público;
  • Administración solo desde red segura;
  • Cuentas de base separadas;
  • HTTPS en el proxy;
  • Logs de autenticación.

Se prueban tres identidades y se documenta qué operaciones puede realizar cada una.

23.1. Matriz de permisos

Construir matriz recurso × rol y justificar al menos cinco decisiones.

23.2. Cuentas

Crear identidades de prueba para público/analista/publicador o equivalentes.

26. Preguntas de cierre

¿Autenticación correcta significa acceso permitido?

No. La autorización se evalúa después y puede denegar un recurso a un usuario autenticado.

¿Por qué no debe compartirse una cuenta administrativa?

Porque elimina trazabilidad individual y dificulta revocar acceso de una sola persona.

¿HTTPS hace segura una aplicación?

Protege la comunicación en tránsito, pero no reemplaza permisos, validación, configuración segura ni monitoreo.

27. Errores frecuentes

  • “Una URL difícil de adivinar está protegida”. La seguridad no debe depender de ocultar rutas.
  • “La cuenta del servicio puede ser superusuario porque solo la usa la aplicación”. Si se compromete, el impacto sería máximo.
  • “Los tokens se pueden escribir en logs para depurar”. Deben protegerse y evitar exposición innecesaria.

31. Síntesis

La Semana 14 transforma políticas de acceso en controles técnicos. Una IDE segura identifica quién accede, limita lo que puede hacer, protege comunicaciones, gestiona credenciales y conserva evidencia suficiente para detectar y analizar eventos.
