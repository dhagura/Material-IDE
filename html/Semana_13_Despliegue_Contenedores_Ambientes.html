Unidad 4 — Despliegue, administración y validación operativa

1. Marco de la semana

La Semana 13 inicia la Unidad 4 con topología de despliegue, ambientes, dependencias, configuración, contenedores o virtualización cuando corresponda y neutralidad respecto del proveedor.

El proyecto deja de ser una colección de componentes configurados manualmente y comienza a tratarse como una infraestructura que debe poder desplegarse, mantenerse y recuperarse de manera reproducible.

2. Propósito

Durante semanas anteriores se publicaron servicios y se construyó una arquitectura lógica. La siguiente pregunta es operacional: ¿podría otro equipo instalar y ejecutar esta IDE a partir de la documentación y artefactos disponibles?

Si la respuesta depende de recordar comandos ejecutados meses atrás, existe una debilidad de mantenibilidad. El despliegue reproducible busca reducir configuración manual, registrar dependencias y separar ambientes.

3. Resultados de aprendizaje

Al finalizar la semana, el estudiante deberá distinguir arquitectura lógica de topología de despliegue, definir ambientes de desarrollo/prueba/producción, documentar dependencias, utilizar contenedores o virtualización de manera fundamentada y construir un despliegue reproducible del proyecto.

También deberá gestionar configuración y secretos sin incorporarlos directamente al código o archivos públicos.

4. ¿Qué es un despliegue?

Desplegar significa llevar una aplicación o servicio desde sus artefactos y configuración hacia un entorno donde puede ejecutarse.

En una IDE, el despliegue puede involucrar:

  • Base de datos;
  • Servidor de mapas;
  • Catálogo;
  • API;
  • Aplicación web;
  • Proxy;
  • Monitoreo;
  • Almacenamiento.

Un despliegue reproducible documenta cómo se conectan y qué configuración requiere cada uno.

5. Ambientes

Separar ambientes reduce el riesgo de probar cambios directamente sobre producción.

Desarrollo

Permite experimentar y modificar componentes con alta frecuencia. Puede utilizar datos reducidos o sintéticos.

Prueba / QA

Busca parecerse a producción y se utiliza para validar versiones antes de liberar cambios.

Producción

Es el entorno utilizado por usuarios y debe priorizar estabilidad, seguridad, respaldo y control de cambios.

No todas las organizaciones necesitan tres infraestructuras físicas completas; el principio puede implementarse con separación lógica proporcional al proyecto.

6. Configuración por ambiente

El código o imagen de aplicación debería mantenerse lo más estable posible entre ambientes; lo que cambia es la configuración.

Ejemplos:

  • URL de base de datos;
  • Dominio;
  • Credenciales;
  • Nivel de logging;
  • Tamaño de caché;
  • Endpoints externos.

Esta separación reduce cambios manuales y facilita promoción entre ambientes.

7. Dependencias

Cada componente depende de versiones de software, bibliotecas, sistema operativo, base, red y configuración.

Un inventario de dependencias debería registrar:

  • Componente;
  • Versión;
  • Origen;
  • Requisito de compatibilidad;
  • Responsable de actualización.

La frase “instalar la última versión” no es reproducible, porque la “última” cambia con el tiempo.

8. Virtualización

Una máquina virtual encapsula un sistema operativo completo sobre un hipervisor. Puede proporcionar aislamiento fuerte y compatibilidad con aplicaciones tradicionales.

Las VMs son útiles cuando los componentes requieren sistemas operativos diferentes, aislamiento de recursos o integración con infraestructura corporativa existente.

Su costo incluye mayor consumo y mantenimiento de sistemas operativos invitados.

9. Contenedores

Los contenedores empaquetan aplicación y dependencias en imágenes que se ejecutan con aislamiento de procesos sobre el host.

Para el curso, Docker puede utilizarse como herramienta docente porque permite describir servicios, redes y volúmenes de forma reproducible. Sin embargo, el concepto importante es contenedorización, no Docker como requisito permanente.

Beneficio

Otro equipo puede ejecutar una imagen equivalente sin repetir manualmente cada instalación.

10. Imagen versus contenedor

La imagen es una plantilla inmutable con software y dependencias. El contenedor es una instancia en ejecución.

Los datos persistentes no deberían depender exclusivamente del sistema de archivos efímero del contenedor. Deben utilizarse volúmenes o almacenamiento externo según la plataforma.

Esta distinción es especialmente importante para PostGIS, catálogos y configuraciones que deben sobrevivir a recreación de contenedores.

11. Docker Compose como herramienta docente

Un archivo Compose puede describir varios servicios y sus relaciones.

services:
  db:
    image: postgis/postgis:...
  geoserver:
    image: ...
    depends_on:
      - db

El ejemplo es conceptual. Las versiones deben fijarse y las imágenes deben provenir de fuentes evaluadas.

Compose ayuda a visualizar arquitectura física, redes, puertos, volúmenes y variables.

12. Redes y puertos

No todos los componentes deben exponerse directamente a internet.

Una topología típica puede mantener base y servicios internos en una red privada y exponer únicamente un proxy o gateway.

flowchart LR U["Usuarios"] --> P["Reverse proxy / HTTPS"] P --> G["GeoServer / API / Catálogo"] G --> D["Base de datos privada"]

Reducir superficie expuesta mejora seguridad y simplifica certificados.

13. Reverse proxy

Un reverse proxy recibe solicitudes externas y las dirige a servicios internos. Puede centralizar TLS, dominios, cabeceras, límites y rutas.

No sustituye autenticación ni seguridad de las aplicaciones, pero simplifica un punto de entrada consistente.

Ejemplo

https://ide.example.cl/maps/ puede dirigir a GeoServer y /api/ a una API distinta sin exponer puertos internos.

14. Configuración y secretos

Las contraseñas, tokens y claves no deberían incorporarse directamente al repositorio de código o imágenes públicas.

Los secretos pueden gestionarse mediante variables protegidas, archivos fuera de control de versiones o servicios especializados según el entorno.

La documentación debe explicar cómo proporcionar secretos sin incluir sus valores reales.

15. Volúmenes y persistencia

Los datos, configuraciones, estilos y catálogos deben identificar qué elementos necesitan persistencia.

Ejemplo

Recrear el contenedor de base no debe eliminar el volumen de datos. Del mismo modo, estilos de GeoServer o registros de catálogo deben incluirse en una estrategia de persistencia y respaldo.

El inventario de persistencia es una entrada directa para Semana 15.

16. Health checks

Un proceso puede estar en ejecución y no estar listo para responder. Los health checks permiten verificar condiciones básicas.

Pueden comprobar:

  • Servicio HTTP;
  • Conexión a base;
  • Disponibilidad de un endpoint;
  • Dependencia crítica.

Un health check no reemplaza monitoreo completo, pero mejora despliegue y recuperación automatizada.

17. Logs en contenedores

Los logs deben salir de los contenedores hacia mecanismos que puedan persistirlos y consultarlos. Si quedan únicamente dentro de una instancia efímera, se perderán al recrearla.

La estrategia debe identificar logs de aplicación, servidor web, base y proxy.

Semana 15 trabajará observabilidad de manera más completa.

18. Actualización de versiones

Fijar versiones mejora reproducibilidad, pero también crea obligación de actualización. La organización necesita un ciclo de revisión de vulnerabilidades, compatibilidad y soporte.

Actualizar directamente producción es riesgoso. El cambio debería probarse primero en un ambiente controlado y disponer de estrategia de rollback.

19. Reproducibilidad

Un despliegue es reproducible cuando otra persona puede reconstruirlo utilizando artefactos y documentación versionada.

Evidencias:

  • Archivo Compose o equivalente;
  • Variables documentadas;
  • Script de inicialización;
  • Migraciones de base;
  • Instrucciones de arranque;
  • Pruebas de salud.

La reproducibilidad es una forma concreta de transferencia de conocimiento.

20. Infraestructura como código

El principio de infraestructura como código consiste en describir recursos mediante archivos versionables en lugar de configurarlos únicamente de forma manual.

En el curso puede aplicarse a Compose y scripts. En entornos más avanzados puede extenderse a herramientas de provisión de nube u orquestación.

El valor pedagógico es registrar decisiones y permitir revisión de cambios.

21. Caso integrador

El proyecto empaqueta:

  • PostGIS;
  • GeoServer o servidor equivalente;
  • Catálogo;
  • API;
  • Proxy.

Los datos persistentes utilizan volúmenes. La base no publica su puerto a internet. El proxy expone HTTPS y las variables sensibles no se guardan en Git.

El equipo puede reconstruir el entorno de prueba en una máquina nueva siguiendo el README.

25. Preguntas de cierre

¿Contenedor significa que no necesito respaldos?

No. Los contenedores son reemplazables; precisamente por eso los datos persistentes deben estar separados y respaldados.

¿Por qué fijar versiones?

Permite reproducir un entorno conocido. Debe combinarse con un proceso de actualización planificado.

¿Todo servicio debe exponer su puerto a internet?

No. Reducir componentes expuestos disminuye superficie de ataque y simplifica control.

26. Errores frecuentes

  • “Docker es la arquitectura”. Es una herramienta de despliegue; la arquitectura existe a nivel lógico y físico más amplio.
  • “Si está en Compose, es producción-ready”. Se necesitan seguridad, respaldo, observabilidad y operación.
  • “Guardar contraseñas en .env y subirlo al repositorio es aceptable”. Los secretos deben excluirse y gestionarse de manera segura.

30. Síntesis

La Semana 13 convierte la IDE en un sistema desplegable. El objetivo no es dominar una herramienta de contenedores, sino aprender a separar configuración, persistencia y dependencias para que la infraestructura pueda reproducirse, actualizarse y recuperarse sin depender de memoria individual.
