Unidad 3 — Publicación de servicios interoperables y APIs geoespaciales

1. Marco de la semana

La Semana 11 aborda acceso a objetos mediante Web Feature Service (WFS) y OGC API - Features, incluyendo colecciones, filtros, paginación, formatos, sistemas de referencia y consultas. El programa busca que el estudiante comprenda tanto servicios OGC clásicos como APIs geoespaciales modernas.

La semana se conecta con WMS: mientras WMS resuelve principalmente representación cartográfica, WFS y OGC API - Features permiten acceder a entidades, geometrías y atributos que pueden ser procesados por el cliente.

2. Propósito

El objetivo es que el estudiante distinga claramente entre ver un mapa y acceder a los objetos que componen ese mapa. Esta diferencia determina arquitectura, rendimiento, permisos y posibles usos.

Un usuario que solo necesita visualizar áreas verdes puede consumir WMS. Un analista que necesita seleccionar polígonos, filtrar atributos y calcular superficies necesita acceso a features. Un desarrollador puede preferir una API basada en HTTP y JSON. La elección debe responder al caso de uso.

3. Resultados de aprendizaje

Al finalizar la semana, el estudiante deberá publicar y consumir al menos un servicio de objetos, interpretar capacidades WFS, consultar colecciones con OGC API - Features, utilizar filtros y paginación, comparar formatos y probar acceso desde clientes distintos.

También deberá analizar riesgos de exponer demasiados atributos o demasiados objetos y aplicar límites de publicación coherentes con las políticas definidas en semanas anteriores.

4. ¿Qué es un feature?

En términos geoespaciales, un feature representa una entidad del mundo real o conceptual con propiedades y, habitualmente, geometría.

Ejemplos:

  • Una plaza;
  • Un tramo vial;
  • Un predio;
  • Una estación de monitoreo;
  • Un permiso asociado a una localización.

El acceso a features permite trabajar con identidad, atributos y geometría, no solo con píxeles renderizados.

5. WFS

WFS es una especificación OGC clásica para acceder a objetos geográficos. Permite descubrir tipos de features y recuperar objetos, normalmente en representaciones como GML u otros formatos soportados por el servidor.

Su modelo de operaciones está bien establecido en infraestructuras OGC tradicionales y continúa siendo relevante para clientes SIG existentes.

La asignatura no busca memorizar todas las posibilidades de WFS, sino comprender las operaciones fundamentales y sus implicancias.

6. GetCapabilities en WFS

El documento de capacidades describe versión, operaciones, formatos y tipos de features disponibles.

Antes de consumir una capa, el estudiante debe revisar:

  • Nombre del feature type;
  • CRS soportados;
  • Formatos de salida;
  • Operaciones disponibles;
  • Restricciones anunciadas.

Esto permite evitar configuraciones basadas en ensayo y error.

7. DescribeFeatureType

En WFS, DescribeFeatureType permite conocer la estructura de los objetos: nombres de atributos, tipos y geometría.

Esta operación resulta importante porque el cliente necesita interpretar la estructura antes de procesar los datos.

Ejemplo

Una capa puede contener id, nombre, tipo, superficie y geom. El esquema documenta tipos y ayuda a validar filtros y transformaciones.

8. GetFeature

GetFeature recupera objetos de uno o más tipos. Puede limitarse mediante identificadores, filtros, BBOX u otras condiciones soportadas.

Sin filtros, solicitar una colección muy grande puede generar respuestas pesadas y afectar servidor y cliente. Por eso los servicios deben incorporar límites y los usuarios deben aprender a formular consultas específicas.

9. Filtros

Los filtros permiten restringir por atributos o condiciones espaciales.

Ejemplo conceptual

Obtener solo áreas verdes cuyo tipo sea PARQUE o que intersecten una extensión determinada.

El servidor ejecuta parte del procesamiento cerca de la fuente, reduciendo transferencia y evitando descargar la colección completa cuando no es necesario.

La seguridad debe impedir que filtros se conviertan en una vía para acceder a atributos o registros no autorizados.

10. Formatos de salida

WFS puede soportar GML, GeoJSON u otros formatos según versión y plataforma.

La selección depende del cliente y del caso de uso. GML ofrece una representación XML muy integrada con estándares OGC; GeoJSON suele ser cómodo para aplicaciones web y herramientas modernas.

El estudiante debe comprobar Content-Type, codificación y compatibilidad real del cliente.

11. OGC API - Features

OGC API - Features define bloques para acceder a colecciones de features mediante patrones web contemporáneos [R2]. La Parte 1 Core se centra en capacidades básicas de consulta.

Una estructura conceptual puede ser:

/
├── conformance
├── collections
├── collections/{collectionId}
└── collections/{collectionId}/items

El usuario puede explorar la landing page, conocer conformidad, descubrir colecciones y consultar items.

12. Landing page y conformance

La landing page funciona como punto inicial y enlaza otras capacidades. El recurso conformance permite conocer qué clases de conformidad declara la implementación.

Esto sigue el principio de hipermedia: el cliente puede descubrir relaciones mediante enlaces en lugar de construir todas las URLs desde conocimiento externo.

Importancia

Una API que entrega datos pero no documenta sus capacidades ni recursos obliga al consumidor a depender de conocimiento manual y reduce interoperabilidad.

13. Collections

Una colección agrupa features relacionados.

El recurso de colección puede informar título, descripción, extensión, CRS y enlaces. Esto permite que el cliente evalúe qué contiene antes de solicitar items.

La colección no debe confundirse necesariamente con una tabla física. La implementación puede exponer una vista o producto derivado y mantener oculto el modelo interno.

14. Items

/collections/{id}/items permite consultar features de la colección. La API puede soportar parámetros de límite, BBOX, fecha y otros filtros según las partes o extensiones implementadas.

El estudiante debe observar que el cliente trabaja con recursos y parámetros HTTP de manera más directa que en muchos servicios OGC clásicos.

15. Paginación

Una API no debería devolver millones de features en una única respuesta. La paginación divide la colección y utiliza enlaces o parámetros para navegar resultados.

La paginación protege servidor, red y cliente, pero el consumidor debe manejarla correctamente. Obtener la primera página no significa haber descargado todo el dataset.

Prueba

Contar objetos de varias páginas y comparar con el número reportado cuando la API lo proporciona.

16. Filtros en OGC API

La familia OGC API permite ampliar capacidades de filtrado mediante estándares complementarios como CQL2 cuando la implementación los soporta.

Para la semana basta comprender que el núcleo permite consultas básicas y que capacidades más avanzadas deben verificarse mediante la declaración de conformidad y documentación del servidor.

No debe asumirse que todos los endpoints implementan las mismas extensiones.

17. Sistemas de referencia

Los features deben interpretarse en un CRS conocido. OGC API - Features define un comportamiento base y extensiones para trabajar con CRS adicionales según implementación.

El estudiante debe comprobar qué CRS recibe y evitar transformar implícitamente sin conocer la referencia.

En clientes web, GeoJSON suele asociarse con coordenadas geográficas en el marco definido por su especificación y práctica de implementación; la documentación del endpoint sigue siendo necesaria.

18. WFS versus OGC API - Features

Aspecto WFS OGC API - Features
Modelo Operaciones OGC clásicas Recursos web
Descubrimiento GetCapabilities Landing page / collections
Estructura DescribeFeatureType Metadatos de colección/esquemas según implementación
Consulta GetFeature /items y parámetros
Ecosistema SIG e IDE existentes Web/API moderna

La comparación no implica que una deba reemplazar inmediatamente a la otra. Una infraestructura puede publicar ambas para distintos consumidores y durante periodos de transición.

19. Seguridad y minimización

Exponer features significa entregar datos, no solo imágenes. Esto eleva el riesgo de transferencia masiva y acceso a atributos sensibles.

Antes de publicar, se debe revisar:

  • Campos expuestos;
  • Número máximo de registros;
  • Filtros permitidos;
  • Nivel de acceso;
  • Necesidad de autenticación;
  • Registros de uso.

La vista de publicación creada en Semana 5 debe ser preferida frente a exponer tablas internas completas.

20. Rendimiento

El rendimiento depende de índices, complejidad geométrica, cantidad de atributos, filtros y tamaño de respuesta.

Un feature con geometría muy detallada puede generar grandes volúmenes incluso si el número de objetos es pequeño. Para ciertos clientes puede ser conveniente utilizar generalización o productos específicos.

La API debería protegerse mediante límites razonables y el cliente debe utilizar consultas selectivas.

21. Descarga versus API

No todos los casos de análisis necesitan una API. Si un usuario requiere procesar todo el dataset de forma desconectada, una descarga completa puede ser más eficiente que recorrer cientos de páginas de una API.

La IDE puede ofrecer ambos mecanismos:

  • API para consulta e integración;
  • Descarga para uso masivo o reproducible.

El catálogo y metadatos deben explicar las opciones.

22. Caso integrador

El grupo publica equipamientos_publicos como WFS y/o OGC API - Features.

La fuente interna contiene campos administrativos; la vista pública expone únicamente identificador, nombre, categoría y geometría.

Casos técnicos guiados — WFS y OGC API - Features

Esta sección desarrolla con detalle la diferencia entre un servicio WFS tradicional y una API moderna de features. Los endpoints son ejemplos de laboratorio y deben sustituirse por los de la implementación real.

Ejemplo 1 — WFS GetCapabilities

curl -o wfs-capabilities.xml \
  "http://localhost:8080/geoserver/municipio/wfs?service=WFS&version=2.0.0&request=GetCapabilities"

La respuesta permite identificar feature types, operaciones y formatos. La documentación de GeoServer señala que WFS soporta operaciones como GetCapabilities, DescribeFeatureType y GetFeature; WFS 2.0 agrega otras capacidades.

Ejemplo 2 — DescribeFeatureType

http://localhost:8080/geoserver/municipio/wfs?
service=WFS&
version=2.0.0&
request=DescribeFeatureType&
typeNames=municipio:areas_verdes

La operación permite conocer la estructura antes de formular consultas. Un cliente puede descubrir que superficie_m2 es numérico y geom es poligonal en vez de asumir tipos.

Ejemplo 3 — GetFeature limitado y en GeoJSON

http://localhost:8080/geoserver/municipio/wfs?
service=WFS&
version=2.0.0&
request=GetFeature&
typeNames=municipio:areas_verdes&
count=10&
outputFormat=application/json

Solicitar count=10 evita transferir toda la colección durante una prueba. En servicios grandes, descargar sin límite puede generar respuestas innecesariamente pesadas.

Ejemplo 4 — Filtrar atributos en GeoServer con ECQL

GeoServer permite cql_filter como extensión del servicio WFS. No debe confundirse con una operación obligatoria de todos los servidores WFS.

http://localhost:8080/geoserver/municipio/wfs?
service=WFS&
version=2.0.0&
request=GetFeature&
typeNames=municipio:areas_verdes&
outputFormat=application/json&
cql_filter=tipo='PARQUE'

Un filtro espacial equivalente puede utilizar INTERSECTS o BBOX, según las capacidades y sintaxis soportadas.

Ejemplo 5 — OGC API - Features: descubrir colecciones

curl -s http://localhost:5000/collections

Una API conforme organiza datos en colecciones. Para inspeccionar una colección concreta:

curl -s http://localhost:5000/collections/areas_verdes

Para navegar features:

curl -s \
  "http://localhost:5000/collections/areas_verdes/items?limit=10"

OGC API - Features Part 1 Core define recursos como landing page, /conformance, /collections, /collections/{collectionId} y /collections/{collectionId}/items.

Ejemplo 6 — Filtro espacial con BBOX

curl -s \
  "http://localhost:5000/collections/areas_verdes/items?bbox=-70.70,-33.55,-70.55,-33.40&limit=20"

El servidor selecciona los features que intersectan la extensión solicitada. El cliente evita descargar objetos fuera de su área de interés.

Ejemplo 7 — Filtro temporal

Si la colección dispone de propiedades temporales compatibles:

curl -s \
  "http://localhost:5000/collections/eventos/items?datetime=2026-09-01/2026-09-30&limit=100"

OGC API - Features Core define datetime para seleccionar features que intersectan un instante o intervalo temporal.

Ejemplo 8 — Paginación

Una respuesta puede incluir un enlace next. La aplicación no debería inventar la URL siguiente cuando el servidor ya la anuncia.

Ejemplo conceptual:

{
  "type": "FeatureCollection",
  "numberReturned": 10,
  "links": [
    {
      "rel": "next",
      "href": "https://api.ejemplo.cl/collections/areas_verdes/items?limit=10&offset=10"
    }
  ]
}

La paginación evita intentar retornar cientos de miles de objetos en una sola respuesta.

Ejemplo 9 — Obtener un feature específico

curl -s \
  http://localhost:5000/collections/areas_verdes/items/AV-0001

Un identificador persistente permite referenciar directamente el mismo objeto.

Ejemplo 10 — Configuración concreta con pygeoapi y PostGIS

Un proveedor PostgreSQL puede configurarse de forma semejante a:

resources:
  areas_verdes:
    type: collection
    title: Áreas verdes públicas
    description: Catastro municipal de áreas verdes activas
    keywords:
      - áreas verdes
      - planificación
    providers:
      - type: feature
        name: PostgreSQL
        data:
          host: postgis
          port: 5432
          dbname: ide
          user: ide_reader
          password: ${IDE_DB_PASSWORD}
          search_path: [publish, public]
        id_field: codigo
        table: areas_verdes
        geom_field: geom

La documentación de pygeoapi confirma el uso de proveedores PostgreSQL/PostGIS con id_field, table y geom_field. En un despliegue real, la contraseña no debería escribirse directamente en el repositorio de configuración.

Ejemplo 11 — Respuesta GeoJSON

{
  "type": "Feature",
  "id": "AV-0001",
  "geometry": {
    "type": "Polygon",
    "coordinates": []
  },
  "properties": {
    "nombre": "Parque Central",
    "tipo": "PARQUE",
    "superficie_m2": 18234.4
  }
}

La geometría se omite en el ejemplo por brevedad; una respuesta real contendrá coordenadas.

Ejemplo 12 — WFS versus OGC API - Features en un caso real

Necesidad WFS OGC API - Features
QGIS institucional existente Muy compatible Depende de cliente/versiones
Desarrollo web moderno Posible, pero XML/GML puede ser menos cómodo JSON/GeoJSON y patrones HTTP naturales
Infraestructura OGC heredada Muy adecuado Puede coexistir
Descubrimiento de recursos por enlaces Menos orientado a hipermedia Parte central del enfoque
Compatibilidad con workflows clásicos Alta Debe evaluarse

La conclusión no debe ser reemplazar siempre WFS. La arquitectura puede ofrecer ambos cuando existen consumidores con necesidades diferentes.

Debe realizarla en WFS y, cuando la implementación lo soporte, en OGC API - Features; comparar URL, formato, tamaño de respuesta, facilidad de interpretación y consumo desde un script o cliente.

26. Preguntas de cierre

¿Por qué WMS y WFS no son equivalentes?

WMS entrega representaciones cartográficas; WFS entrega objetos y atributos que pueden procesarse.

¿Por qué la paginación es importante?

Protege servidor y clientes y permite navegar colecciones grandes sin transferir todo en una única respuesta.

¿Una API debe exponer la tabla interna completa?

No. Es preferible publicar un contrato estable y mínimo, desacoplado de estructuras internas y coherente con políticas de acceso.

27. Errores frecuentes

  • “Si necesito todos los datos, siempre debo usar API”. Una descarga completa puede ser más apropiada para procesamiento masivo.
  • “La primera página contiene toda la colección”. Debe revisarse paginación.
  • “WFS es simplemente WMS en vector”. Sus modelos y objetivos son diferentes.
  • “Más atributos publicados ofrecen más valor”. También aumentan acoplamiento, transferencia y riesgo.
