Unidad 3 — Publicación de servicios interoperables y APIs geoespaciales

1. Marco de la semana

La Semana 9 inicia la Unidad 3 con los principios HTTP, recursos, solicitudes, respuestas, formatos, codificación, documentos de capacidades y manejo de errores. El objetivo es construir una base web común antes de estudiar WMS, WFS y OGC API.

Muchos estudiantes pueden haber consumido servicios desde QGIS sin observar qué ocurre en la red. Esta semana abre esa “caja negra”.

2. Propósito

Comprender HTTP permite interpretar servicios OGC clásicos y APIs modernas. Una URL WMS, una petición a collections/{id}/items y un error 404 son manifestaciones de los mismos fundamentos web.

La meta no es convertir el curso en desarrollo web general, sino dar al estudiante herramientas para diagnosticar interoperabilidad sin depender exclusivamente de una interfaz gráfica.

3. Resultados de aprendizaje

Al finalizar la semana, el estudiante deberá reconocer componentes de una URL, métodos HTTP, códigos de estado, cabeceras, tipos de contenido, parámetros, codificación y estructura general de solicitudes/respuestas.

También deberá utilizar navegador, curl o una herramienta equivalente para inspeccionar servicios y diferenciar errores de cliente, servidor, autenticación, formato y recurso inexistente.

4. Modelo cliente-servidor

sequenceDiagram participant C as Cliente participant S as Servidor C->>S: Solicitud HTTP S->>C: Respuesta HTTP

El cliente puede ser QGIS, un navegador, una aplicación web o un script. El servidor procesa la solicitud y responde con datos, una imagen, un documento o un error.

La interoperabilidad depende de que ambas partes compartan reglas de comunicación suficientemente precisas.

5. Anatomía de una URL

Una URL puede contener esquema, host, puerto, ruta, consulta y fragmento.

https://geo.ejemplo.cl/geoserver/wms?service=WMS&request=GetCapabilities
  • Esquema. https indica el protocolo y protección de la comunicación.
  • Host. geo.ejemplo.cl identifica el servidor o dominio.
  • Ruta. /geoserver/wms identifica un recurso o endpoint.
  • Query string. Los parámetros posteriores a ? entregan información adicional.

Comprender esta estructura permite diagnosticar si el problema está en dominio, ruta o parámetros.

6. Métodos HTTP

Los métodos indican la intención de la solicitud.

  • GET. Recupera una representación o recurso y es frecuente en consultas de servicios geoespaciales.
  • POST. Envía una representación o solicitud en el cuerpo; puede utilizarse para consultas complejas o creación según la API.
  • PUT/PATCH. Se utilizan en APIs que permiten actualizar recursos.
  • DELETE. Solicita eliminación cuando la interfaz lo soporta.

Los servicios OGC de publicación vistos en el curso se concentrarán principalmente en lectura, pero comprender el modelo ayuda a interpretar APIs.

7. Solicitudes

Una solicitud HTTP contiene método, URL, cabeceras y, en algunos casos, cuerpo.

Ejemplo con curl

curl -i "https://servidor.example/endpoint"

La opción -i permite observar cabeceras de respuesta. Durante el laboratorio se utilizarán endpoints reales disponibles para el curso.

8. Respuestas

Una respuesta contiene código de estado, cabeceras y cuerpo.

HTTP/1.1 200 OK
Content-Type: application/json

{ ... }

El cliente debe interpretar no solo el cuerpo. El código y tipo de contenido indican qué ocurrió y cómo procesar la respuesta.

9. Códigos de estado

9.1. 2xx — Éxito

200 OK indica que la solicitud se procesó correctamente. Otros códigos pueden expresar creación o ausencia de cuerpo según la operación.

9.2. 4xx — Problemas asociados a la solicitud

400 suele indicar una petición inválida; 401 falta de autenticación válida; 403 acceso prohibido; 404 recurso no encontrado.

9.3. 5xx — Error de servidor

Indican que el servidor no pudo completar una solicitud que llegó hasta él. Un 500 no debe resolverse simplemente reintentando indefinidamente; requiere revisar logs o configuración.

Los códigos ayudan a dirigir diagnóstico hacia cliente, permisos, rutas o servidor.

10. Cabeceras

Las cabeceras transmiten metainformación de la comunicación.

Ejemplos:

  • Content-Type indica el tipo del cuerpo.
  • Accept expresa formatos que el cliente prefiere.
  • Authorization puede transportar credenciales o tokens.
  • Cabeceras de caché controlan reutilización de respuestas.

Una API bien diseñada permite negociar representaciones sin inferir formatos solo por extensiones de archivo.

11. Tipos de contenido

Los servicios geoespaciales pueden devolver XML, JSON, GeoJSON, PNG, JPEG, GML u otros formatos.

El Content-Type debe ser coherente con el contenido. Un problema común es recibir una página HTML de error cuando el cliente esperaba JSON; observar la cabecera ayuda a identificarlo rápidamente.

12. Parámetros de consulta y codificación

Los parámetros viajan con frecuencia en la query string. Caracteres especiales deben codificarse adecuadamente.

Ejemplo conceptual

?service=WMS&request=GetMap&layers=municipio:areas_verdes

El orden puede no ser importante según el protocolo, pero nombres, valores y codificación sí lo son.

13. Documentos de capacidades

Los servicios OGC clásicos suelen ofrecer documentos de capacidades que describen operaciones, formatos, capas, CRS y otros elementos.

En lugar de adivinar qué soporta un servidor, el cliente consulta sus capacidades.

sequenceDiagram participant C as Cliente participant S as Servidor OGC C->>S: GetCapabilities S->>C: Documento XML de capacidades C->>C: Descubre capas, formatos y operaciones

La Semana 10 profundizará el caso de WMS.

14. Descubrimiento en OGC API

Las APIs modernas tienden a proporcionar recursos como landing page, declaración de conformidad y colecciones.

El principio es similar al documento de capacidades: el cliente necesita descubrir qué ofrece el servidor, pero la organización de la interfaz se alinea con patrones web contemporáneos.

OGC API - Common define bloques compartidos para esta familia [R2].

15. Formatos geoespaciales en web

JSON y GeoJSON

Son comunes en APIs y aplicaciones web. GeoJSON representa features, geometrías y propiedades en una estructura ampliamente soportada.

XML y GML

Han sido fundamentales en servicios OGC clásicos y continúan presentes en interoperabilidad existente.

Imágenes

PNG y JPEG son comunes en servicios de mapas. PNG soporta transparencia, mientras JPEG puede ser más apropiado para imágenes continuas cuando no se necesita canal alfa.

El formato debe seleccionarse por propósito, no por preferencia personal.

16. Errores geoespaciales versus errores HTTP

Un servicio puede devolver 200 OK y contener una respuesta de excepción en el cuerpo según el protocolo. También puede devolver un código HTTP de error.

Por eso el diagnóstico debe revisar ambos niveles: transporte HTTP y semántica del estándar geoespacial.

Ejemplo

Una capa inexistente puede generar un documento XML de excepción. QGIS puede mostrar un mensaje genérico; inspeccionar la respuesta ayuda a conocer la causa real.

17. Idempotencia y caché

Una operación de consulta debería poder repetirse sin modificar el estado del servidor. Esta propiedad facilita pruebas y caché.

La caché reutiliza respuestas cuando siguen siendo válidas y puede reducir carga de servicios cartográficos. Sin embargo, debe controlarse vigencia: una respuesta almacenada puede mostrar una versión antigua después de actualizar la fuente.

Estos conceptos se profundizarán en Semana 12.

18. HTTPS

HTTPS protege la comunicación mediante TLS. Debe utilizarse para evitar exposición de credenciales y contenido en tránsito, especialmente en servicios autenticados.

La seguridad no depende solo de “tener el candado”. Certificados deben ser válidos, renovarse, utilizar configuraciones apropiadas y combinarse con autenticación/autorización adecuadas.

Semana 14 profundizará estos aspectos.

19. Herramientas de inspección

El estudiante debe aprender a observar la red utilizando herramientas simples:

  • Navegador y barra de direcciones;
  • Herramientas de desarrollo del navegador;
  • curl;
  • Cliente API como Postman/Insomnia si está disponible;
  • QGIS para comparar comportamiento de un cliente SIG.

La herramienta es secundaria. La habilidad importante es poder leer solicitud y respuesta.

20. Caso de diagnóstico

QGIS no carga una capa WMS.

El estudiante debe revisar:

  1. ¿resuelve el dominio?;
  2. ¿responde HTTPS?;
  3. ¿GetCapabilities devuelve contenido?;
  4. ¿el Content-Type es esperado?;
  5. ¿aparece la capa?;
  6. ¿el nombre solicitado es correcto?;
  7. ¿existe autenticación?;
  8. ¿el servidor devuelve una excepción?

Este flujo es más efectivo que cambiar configuraciones al azar.

21. Laboratorio 9 — Inspección HTTP

21.1. Solicitud básica

Consultar un endpoint y registrar URL, método, código, cabeceras y cuerpo.

21.2. GetCapabilities

Solicitar capacidades de un servicio OGC disponible y localizar versión, operaciones y capas.

21.3. Error controlado

Modificar deliberadamente un parámetro o nombre de recurso para observar el error.

Comparar una respuesta XML y JSON cuando existan endpoints apropiados.

24. Preguntas de cierre

¿Un 200 significa siempre que el dato es correcto?

No. Indica éxito HTTP, pero el contenido puede ser incorrecto desde la perspectiva geoespacial o del usuario.

¿Para qué sirve Content-Type?

Permite al cliente conocer la representación recibida y decidir cómo interpretarla.

¿Por qué estudiar HTTP si QGIS ya consume servicios?

Porque permite diagnosticar problemas, comprender interoperabilidad y trabajar con APIs y clientes distintos.

25. Errores frecuentes

  • “404 Significa que internet no funciona”. Significa que el servidor no encontró el recurso solicitado; la red puede estar funcionando perfectamente.
  • “XML es un error”. Muchos estándares OGC clásicos utilizan XML como representación normal.
  • “Si QGIS falla, el servidor está caído”. Deben inspeccionarse solicitud, permisos, formato y respuesta antes de concluir.
