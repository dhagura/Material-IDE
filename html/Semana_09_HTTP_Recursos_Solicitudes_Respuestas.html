Unidad 3 — Publicación de servicios interoperables y APIs geoespaciales

1. Marco de la semana

La Semana 9 inicia la Unidad 3 con los principios HTTP, recursos, solicitudes, respuestas, formatos, codificación, documentos de capacidades y manejo de errores. El objetivo es construir una base web común antes de estudiar WMS, WFS y OGC API.

Muchos estudiantes pueden haber consumido servicios desde QGIS sin observar qué ocurre en la red. Esta semana abre esa “caja negra”.

2. Propósito

Comprender HTTP permite interpretar servicios OGC clásicos y APIs modernas. Una URL WMS, una petición a collections/{id}/items y un error 404 son manifestaciones de los mismos fundamentos web.

La meta no es convertir el curso en desarrollo web general, sino dar al estudiante herramientas para diagnosticar interoperabilidad sin depender exclusivamente de una interfaz gráfica.

3. Resultados de aprendizaje

Al finalizar la semana, el estudiante deberá reconocer componentes de una URL, métodos HTTP, códigos de estado, cabeceras, tipos de contenido, parámetros, codificación y estructura general de solicitudes/respuestas.

También deberá utilizar navegador, curl o una herramienta equivalente para inspeccionar servicios y diferenciar errores de cliente, servidor, autenticación, formato y recurso inexistente.

4. Modelo cliente-servidor

sequenceDiagram
    participant C as Cliente
    participant S as Servidor
    C->>S: Solicitud HTTP
    S->>C: Respuesta HTTP

El cliente puede ser QGIS, un navegador, una aplicación web o un script. El servidor procesa la solicitud y responde con datos, una imagen, un documento o un error.

La interoperabilidad depende de que ambas partes compartan reglas de comunicación suficientemente precisas.

5. Anatomía de una URL

Una URL puede contener esquema, host, puerto, ruta, consulta y fragmento.

https://geo.ejemplo.cl/geoserver/wms?service=WMS&request=GetCapabilities
  • Esquema. https indica el protocolo y protección de la comunicación.
  • Host. geo.ejemplo.cl identifica el servidor o dominio.
  • Ruta. /geoserver/wms identifica un recurso o endpoint.
  • Query string. Los parámetros posteriores a ? entregan información adicional.

Comprender esta estructura permite diagnosticar si el problema está en dominio, ruta o parámetros.

6. Métodos HTTP

Los métodos indican la intención de la solicitud.

  • GET. Recupera una representación o recurso y es frecuente en consultas de servicios geoespaciales.
  • POST. Envía una representación o solicitud en el cuerpo; puede utilizarse para consultas complejas o creación según la API.
  • PUT/PATCH. Se utilizan en APIs que permiten actualizar recursos.
  • DELETE. Solicita eliminación cuando la interfaz lo soporta.

Los servicios OGC de publicación vistos en el curso se concentrarán principalmente en lectura, pero comprender el modelo ayuda a interpretar APIs.

7. Solicitudes

Una solicitud HTTP contiene método, URL, cabeceras y, en algunos casos, cuerpo.

Ejemplo con curl

curl -i "https://servidor.example/endpoint"

La opción -i permite observar cabeceras de respuesta. Durante el laboratorio se utilizarán endpoints reales disponibles para el curso.

8. Respuestas

Una respuesta contiene código de estado, cabeceras y cuerpo.

HTTP/1.1 200 OK
Content-Type: application/json

{ ... }

El cliente debe interpretar no solo el cuerpo. El código y tipo de contenido indican qué ocurrió y cómo procesar la respuesta.

9. Códigos de estado

9.1. 2xx — Éxito

Los códigos 2xx indican que el servidor procesó satisfactoriamente la solicitud, aunque cada código puede expresar un resultado distinto. 200 OK es habitual para consultas que devuelven contenido; 201 Created puede utilizarse cuando se crea un recurso y 204 No Content cuando la operación fue exitosa pero no necesita devolver cuerpo.

En una IDE, observar solamente que “no hubo error” es insuficiente. El cliente también debe verificar Content-Type, estructura y contenido esperado. Una API puede devolver 200 con una colección vacía porque el BBOX no intersecta datos, lo cual es diferente de una falla.

9.2. 4xx — Problemas asociados a la solicitud

Los códigos 4xx indican que el servidor recibió la solicitud, pero existe un problema relacionado con lo que el cliente pidió o con sus credenciales. 400 Bad Request suele representar parámetros mal formados; 401 Unauthorized, falta de autenticación válida; 403 Forbidden, identidad autenticada sin permiso; y 404 Not Found, recurso inexistente.

El diagnóstico debe comenzar por revisar URL, parámetros, formato, autenticación y autorización antes de atribuir el problema a una caída del servidor. Una respuesta bien diseñada debería aportar suficiente contexto para corregir la solicitud.

9.3. 5xx — Error de servidor

Los códigos 5xx indican que el servidor o alguna dependencia impidió completar una solicitud. 500 Internal Server Error suele reflejar una excepción no controlada, mientras 502, 503 o 504 pueden aparecer cuando intervienen proxies, servicios no disponibles o tiempos de espera agotados.

Un 500 no debe resolverse simplemente reintentando indefinidamente. El administrador debe revisar logs, estado de base de datos, conectividad y cambios recientes. La clasificación HTTP ayuda a orientar el diagnóstico hacia solicitud, permisos, rutas o infraestructura.

10. Cabeceras

Las cabeceras transmiten metainformación de la comunicación.

Ejemplos:

  • Content-Type indica el tipo del cuerpo.
  • Accept expresa formatos que el cliente prefiere.
  • Authorization puede transportar credenciales o tokens.
  • Cabeceras de caché controlan reutilización de respuestas.

Una API bien diseñada permite negociar representaciones sin inferir formatos solo por extensiones de archivo.

11. Tipos de contenido

Los servicios geoespaciales pueden devolver XML, JSON, GeoJSON, PNG, JPEG, GML u otros formatos.

El Content-Type debe ser coherente con el contenido. Un problema común es recibir una página HTML de error cuando el cliente esperaba JSON; observar la cabecera ayuda a identificarlo rápidamente.

12. Parámetros de consulta y codificación

Los parámetros viajan con frecuencia en la query string. Caracteres especiales deben codificarse adecuadamente.

Ejemplo conceptual

?service=WMS&request=GetMap&layers=municipio:areas_verdes

El orden puede no ser importante según el protocolo, pero nombres, valores y codificación sí lo son.

13. Documentos de capacidades

Los servicios OGC clásicos suelen ofrecer documentos de capacidades que describen operaciones, formatos, capas, CRS y otros elementos.

En lugar de adivinar qué soporta un servidor, el cliente consulta sus capacidades.

sequenceDiagram
    participant C as Cliente
    participant S as Servidor OGC
    C->>S: GetCapabilities
    S->>C: Documento XML de capacidades
    C->>C: Descubre capas, formatos y operaciones

La Semana 10 profundizará el caso de WMS.

14. Descubrimiento en OGC API

Las APIs modernas tienden a proporcionar recursos como landing page, declaración de conformidad y colecciones.

El principio es similar al documento de capacidades: el cliente necesita descubrir qué ofrece el servidor, pero la organización de la interfaz se alinea con patrones web contemporáneos.

OGC API - Common define bloques compartidos para esta familia [R2].

15. Formatos geoespaciales en web

JSON y GeoJSON

JSON es un formato de intercambio estructurado muy utilizado por APIs web. GeoJSON define una convención específica para representar Feature, FeatureCollection, geometrías y propiedades geográficas. Su legibilidad y compatibilidad con bibliotecas web lo hacen especialmente útil para aplicaciones ligeras y OGC API - Features.

Sin embargo, no debe asumirse que GeoJSON es óptimo para cualquier volumen. Colecciones muy grandes pueden requerir paginación, otras representaciones o mecanismos de descarga más eficientes.

XML y GML

XML continúa siendo fundamental en numerosos servicios OGC clásicos. GML utiliza XML para representar features, geometrías, sistemas de referencia y estructuras complejas. Documentos GetCapabilities, esquemas y respuestas WFS tradicionales pueden depender de esta familia.

El estudiante no necesita memorizar toda la sintaxis, pero sí identificar namespaces, elementos principales y mensajes de excepción para diagnosticar interoperabilidad.

Imágenes

PNG y JPEG son comunes en servicios de mapas. PNG soporta transparencia y preserva bien líneas y simbología discreta, mientras JPEG puede reducir tamaño en ortofotos o imágenes continuas cuando se acepta compresión con pérdida y no se necesita canal alfa.

El formato debe seleccionarse por propósito. Una capa temática destinada a superponerse sobre un mapa base suele beneficiarse de PNG transparente; una ortofoto de fondo puede ser más eficiente en JPEG.

16. Errores geoespaciales versus errores HTTP

Un servicio puede devolver 200 OK y contener una respuesta de excepción en el cuerpo según el protocolo. También puede devolver un código HTTP de error.

Por eso el diagnóstico debe revisar ambos niveles: transporte HTTP y semántica del estándar geoespacial.

Ejemplo

Una capa inexistente puede generar un documento XML de excepción. QGIS puede mostrar un mensaje genérico; inspeccionar la respuesta ayuda a conocer la causa real.

17. Idempotencia y caché

Una operación de consulta debería poder repetirse sin modificar el estado del servidor. Esta propiedad facilita pruebas y caché.

La caché reutiliza respuestas cuando siguen siendo válidas y puede reducir carga de servicios cartográficos. Sin embargo, debe controlarse vigencia: una respuesta almacenada puede mostrar una versión antigua después de actualizar la fuente.

Estos conceptos se profundizarán en Semana 12.

18. HTTPS

HTTPS protege la comunicación mediante TLS. Debe utilizarse para evitar exposición de credenciales y contenido en tránsito, especialmente en servicios autenticados.

La seguridad no depende solo de “tener el candado”. Certificados deben ser válidos, renovarse, utilizar configuraciones apropiadas y combinarse con autenticación/autorización adecuadas.

Semana 14 profundizará estos aspectos.

19. Herramientas de inspección

El estudiante debe aprender a observar la red utilizando herramientas simples:

  • Navegador y barra de direcciones;
  • Herramientas de desarrollo del navegador;
  • curl;
  • Cliente API como Postman/Insomnia si está disponible;
  • QGIS para comparar comportamiento de un cliente SIG.

La herramienta es secundaria. La habilidad importante es poder leer solicitud y respuesta.

20. Caso de diagnóstico

QGIS no carga una capa WMS.

El estudiante debe revisar:

  1. ¿resuelve el dominio?;
  2. ¿responde HTTPS?;
  3. ¿GetCapabilities devuelve contenido?;
  4. ¿el Content-Type es esperado?;
  5. ¿aparece la capa?;
  6. ¿el nombre solicitado es correcto?;
  7. ¿existe autenticación?;
  8. ¿el servidor devuelve una excepción?

Este flujo es más efectivo que cambiar configuraciones al azar.

Casos técnicos guiados — HTTP aplicado a servicios geoespaciales

Comprender HTTP resulta mucho más sencillo cuando se observa una solicitud real y se separan sus componentes. Los ejemplos utilizan curl porque permite visualizar la interacción sin ocultarla detrás de una interfaz gráfica.

Ejemplo 1 — Inspeccionar cabeceras y estado

curl -i https://api.ejemplo.cl/collections

Una respuesta típica comienza con información semejante a:

HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 1842
Cache-Control: max-age=60

El código 200 indica que la solicitud fue atendida. Content-Type comunica cómo interpretar el cuerpo. Un cliente no debería asumir que toda respuesta es JSON.

Ejemplo 2 — Negociación de representación

curl -H "Accept: application/json" \
  https://api.ejemplo.cl/collections

En una API que también ofrece HTML, un navegador podría recibir una página legible por personas y un cliente automatizado solicitar JSON. Esta capacidad ayuda a servir diferentes consumidores desde un mismo recurso conceptual.

Ejemplo 3 — Query parameters

https://api.ejemplo.cl/collections/areas_verdes/items?limit=10&bbox=-70.70,-33.55,-70.55,-33.40

La URL contiene:

Esquema:  https
Host:     api.ejemplo.cl
Ruta:     /collections/areas_verdes/items
Query:    limit=10&bbox=...

Los parámetros modifican la selección o representación, pero el recurso principal sigue siendo la colección de items.

Ejemplo 4 — Codificación de caracteres

Una búsqueda áreas verdes no debería insertarse manualmente con espacios y caracteres especiales. Puede codificarse como:

q=%C3%A1reas%20verdes

Las librerías HTTP realizan normalmente esta codificación, pero comprenderla ayuda a diagnosticar URLs que fallan.

Ejemplo 5 — GeoJSON como respuesta

{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "id": "AV-0001",
      "geometry": {
        "type": "Point",
        "coordinates": [-70.6501, -33.4412]
      },
      "properties": {
        "nombre": "Plaza Ejemplo",
        "tipo": "PLAZA"
      }
    }
  ]
}

El formato permite distinguir colección, feature, geometría y propiedades. El cliente debe verificar además el CRS definido por el estándar o anunciado por la API.

Ejemplo 6 — Errores HTTP que deben interpretarse

Código Significado general Ejemplo IDE
200 Solicitud exitosa Colección devuelta
400 Solicitud inválida BBOX mal formado
401 Falta autenticación válida Token ausente
403 Identidad sin autorización Usuario autenticado intenta recurso restringido
404 Recurso no encontrado collectionId inexistente
406 Representación no aceptable Accept no soportado
429 Demasiadas solicitudes Límite de uso excedido
500 Error interno Fallo no controlado en servidor
503 Servicio no disponible Backend temporalmente fuera de operación

La distinción 401 versus 403 será retomada en seguridad: el primero se relaciona con autenticación; el segundo con autorización.

Ejemplo 7 — Medir tiempos con curl

curl -s -o /dev/null \
  -w "status=%{http_code} total=%{time_total}s size=%{size_download}B\n" \
  "https://api.ejemplo.cl/collections/areas_verdes/items?limit=100"

Este comando produce evidencia cuantitativa para pruebas de rendimiento básicas.

Ejemplo 8 — Probar contenido inválido

curl -i \
  "https://api.ejemplo.cl/collections/areas_verdes/items?limit=-1"

El objetivo no es provocar fallas destructivas, sino verificar que el servidor rechaza parámetros fuera de rango con un error comprensible y no con una excepción genérica.

Ejemplo 9 — OpenAPI como contrato de API

Una API moderna puede exponer una definición OpenAPI donde se describen rutas, parámetros, respuestas y esquemas. El estudiante debe aprender a distinguir entre:

  • Documentación legible por personas. Explica con lenguaje y ejemplos cómo debería utilizarse la API y qué significado tienen sus recursos.
  • Definición legible por herramientas. Una especificación OpenAPI puede ser utilizada por interfaces Swagger, generadores de clientes y validadores automáticos.
  • Comportamiento real del servidor. La implementación debe responder de acuerdo con lo documentado; una definición perfecta no compensa endpoints que devuelven otra estructura o códigos inesperados.

Las tres deben ser coherentes. Durante la validación conviene comparar una operación documentada con la respuesta real del servidor.

Ejercicio guiado

Para un endpoint del laboratorio, ejecutar cinco solicitudes: una exitosa, una con BBOX, una con Accept, una con parámetro inválido y una a un recurso inexistente. Guardar comando, código HTTP, Content-Type, tiempo y una interpretación de la respuesta.

24. Preguntas de cierre

¿Un 200 significa siempre que el dato es correcto?

No. Indica éxito HTTP, pero el contenido puede ser incorrecto desde la perspectiva geoespacial o del usuario.

¿Para qué sirve Content-Type?

Permite al cliente conocer la representación recibida y decidir cómo interpretarla.

¿Por qué estudiar HTTP si QGIS ya consume servicios?

Porque permite diagnosticar problemas, comprender interoperabilidad y trabajar con APIs y clientes distintos.

25. Errores frecuentes

  • “404 Significa que internet no funciona”. Significa que el servidor no encontró el recurso solicitado; la red puede estar funcionando perfectamente.
  • “XML es un error”. Muchos estándares OGC clásicos utilizan XML como representación normal.
  • “Si QGIS falla, el servidor está caído”. Deben inspeccionarse solicitud, permisos, formato y respuesta antes de concluir.
