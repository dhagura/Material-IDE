Unidad 3 — Publicación de servicios interoperables y APIs geoespaciales

1. Marco de la semana

La Semana 10 profundiza Web Map Service (WMS): capas, estilos, leyendas, escalas, sistemas de referencia, dimensiones y operaciones principales. El programa incluye explícitamente WMS 1.3.0 en la bibliografía base.

La meta es que el estudiante comprenda WMS como un contrato interoperable para solicitar representaciones cartográficas y no solamente como una casilla que se activa en GeoServer.

2. Propósito

WMS permite que un cliente solicite un mapa renderizado a un servidor. El cliente no necesita descargar el dataset completo ni conocer cómo está almacenado.

Esto facilita visualización interoperable, pero también implica límites: WMS entrega principalmente imágenes de mapa, no reemplaza servicios de features cuando el usuario necesita objetos y atributos completos.

3. Resultados de aprendizaje

El estudiante deberá publicar y consumir WMS, interpretar GetCapabilities, construir solicitudes GetMap y GetFeatureInfo, configurar estilos y leyendas, manejar CRS y escalas, probar dimensiones cuando corresponda y diagnosticar errores de parámetros.

También deberá justificar cuándo WMS es apropiado y cuándo se necesita otro tipo de servicio.

4. Modelo conceptual WMS

El servidor controla el renderizado. El cliente solicita capas, área, tamaño, CRS, formato y estilo dentro de lo permitido por la especificación y configuración.

5. GetCapabilities

GetCapabilities describe qué ofrece el servicio. El documento puede incluir:

  • Versión;
  • Operaciones;
  • Formatos;
  • Capas;
  • Jerarquías;
  • Títulos;
  • Estilos;
  • CRS;
  • Extensiones y dimensiones.

El documento es una fuente de verdad técnica para el cliente. Antes de construir una solicitud, conviene revisar qué nombres exactos y capacidades declara.

6. Nombre, título y abstracción de capa

Una capa puede tener un nombre técnico utilizado en solicitudes y un título legible para usuarios.

Ejemplo

Name: municipio:areas_verdes
Title: Áreas verdes públicas

Confundir ambos valores genera errores. El título puede cambiar para mejorar presentación; el nombre técnico debería mantenerse estable cuando existen clientes configurados.

7. GetMap

GetMap solicita una imagen cartográfica para una extensión y tamaño.

Los parámetros principales incluyen servicio, versión, operación, capas, estilos, CRS, BBOX, ancho, alto y formato.

Ejemplo conceptual

?SERVICE=WMS
&VERSION=1.3.0
&REQUEST=GetMap
&LAYERS=municipio:areas_verdes
&CRS=EPSG:4326
&BBOX=...
&WIDTH=1024
&HEIGHT=768
&FORMAT=image/png

La solicitud completa debe respetar la sintaxis y el orden de ejes definido para el CRS y versión correspondiente.

8. BBOX y extensión

El BBOX define el rectángulo de mapa solicitado. Debe interpretarse en el CRS indicado.

Un error de orden o unidades puede producir mapas vacíos o aparentemente desplazados. En WMS 1.3.0, el tratamiento de ejes para determinados CRS como EPSG:4326 requiere especial atención.

Esta es una razón importante para no construir URLs únicamente por ensayo y error.

9. CRS en WMS

El servidor puede anunciar múltiples CRS. El cliente solicita uno compatible y el servidor transforma la representación cuando está configurado para ello.

La reproyección en tiempo de renderizado facilita interoperabilidad, pero puede tener costo de rendimiento y no corrige una fuente con CRS incorrectamente definido.

Principio

La fuente debe estar correctamente referenciada antes de publicar. El servicio no debe utilizarse para ocultar errores de datos.

10. Formatos de imagen

PNG

PNG es adecuado para cartografía con áreas planas, líneas, texto y transparencia. Al utilizar compresión sin pérdida conserva bordes y simbología con buena calidad y puede mantener canal alfa para superponer una capa temática sobre otra fuente.

Como contrapartida, una imagen PNG puede pesar más que JPEG cuando contiene variaciones continuas de color, por ejemplo una ortofoto. Por eso la selección debe relacionarse con el tipo de contenido.

JPEG

JPEG es adecuado para imágenes continuas como ortofotos cuando no se necesita transparencia y se acepta compresión con pérdida. Puede producir archivos sensiblemente más pequeños que PNG en contenido fotográfico, pero genera artefactos en bordes, texto y símbolos de alto contraste.

La selección afecta calidad, tamaño de respuesta y composición en el cliente. Un WMS puede ofrecer varios formatos y permitir que el consumidor elija según el contexto.

11. Estilos

El estilo controla cómo el servidor representa los datos.

Un mismo dataset puede tener varios estilos para propósitos distintos: jerarquía vial, estado de conservación, uso público o análisis temático.

El estilo debe considerar:

  • Variables visuales;
  • Escalas;
  • Legibilidad;
  • Contraste;
  • Leyenda;
  • Costo de renderizado.

La simbología también comunica significado y puede inducir a error si exagera diferencias o utiliza categorías ambiguas.

12. Escalas de visibilidad

No toda información debe mostrarse a todas las escalas. Las etiquetas y objetos detallados pueden saturar el mapa cuando el usuario está muy alejado.

Configurar escalas de visibilidad reduce ruido y puede mejorar rendimiento.

Ejemplo

Las calles locales aparecen solo al acercarse, mientras las vías principales se mantienen visibles a escalas menores.

El criterio debe responder a la finalidad cartográfica y no simplemente a una preferencia estética.

13. Leyendas

Una leyenda permite interpretar estilos y categorías. Puede generarse mediante mecanismos del servidor o exponerse como recurso asociado.

La leyenda debe corresponder con el estilo realmente aplicado. Si la simbología cambia y la leyenda no se actualiza, el mapa se vuelve engañoso.

La prueba debe verificar legibilidad y coherencia en clientes independientes.

14. GetFeatureInfo

GetFeatureInfo permite solicitar información sobre una ubicación del mapa para capas consultables. La operación depende de una solicitud de mapa y coordenadas dentro de la imagen.

No debe confundirse con acceso completo a features. Es una consulta puntual vinculada a la representación cartográfica.

Cuándo es útil

Visores que necesitan mostrar atributos al hacer clic sin descargar toda la capa.

Cuándo no reemplaza WFS/API

Cuando el usuario necesita filtrar, descargar o procesar colecciones completas de objetos.

15. Dimensiones

WMS puede trabajar con dimensiones adicionales como tiempo o elevación cuando el servidor y la capa están configurados.

Ejemplo temporal

Un dataset de precipitación mensual puede permitir seleccionar un periodo o instante.

La dimensión debe estar documentada en capacidades y sus valores deben relacionarse con la fuente real.

16. Capas agrupadas

Los servidores pueden exponer grupos de capas para facilitar consumo de composiciones completas. Esto puede simplificar usuarios, pero aumenta acoplamiento si el grupo contiene demasiadas decisiones específicas.

La arquitectura debe decidir si conviene publicar capas individuales, grupos o ambos según casos de uso.

17. Seguridad en WMS

Un WMS puede ser público o restringido. La restricción puede aplicarse por servicio, capa o grupo según la plataforma.

La autenticación debe utilizar HTTPS y credenciales institucionales. No deben incluirse claves permanentes directamente en URLs públicas.

Semana 14 profundizará seguridad, pero desde ahora debe comprobarse que la clasificación de Semana 3 se respeta.

18. Rendimiento

El rendimiento depende de fuente, índices, estilos, tamaño de imagen, complejidad geométrica, reproyección y concurrencia.

Un estilo con etiquetas complejas sobre millones de objetos puede ser mucho más costoso que una simbología simple.

Antes de asumir que “GeoServer es lento” u otro servidor es el problema, se debe medir dónde se consume tiempo.

Semana 12 trabajará caché y teselas.

19. Manejo de errores

Errores frecuentes incluyen capa inexistente, CRS no soportado, BBOX inválido, formato no permitido o parámetros ausentes.

El estudiante debe inspeccionar la respuesta del servidor y no depender solo del mensaje del cliente. Un documento de excepción suele contener información más específica.

Flujo

  1. Probar GetCapabilities.
  2. Verificar nombre de capa.
  3. Revisar CRS y extensión.
  4. Simplificar solicitud.
  5. Revisar logs si el error es servidor.

20. Prueba desde clientes independientes

El programa exige pruebas desde clientes independientes. Un WMS no está suficientemente verificado si solo funciona en la interfaz administrativa del servidor.

Se debe probar al menos desde:

  • QGIS u otro SIG de escritorio;
  • Navegador/URL para inspección;
  • Cliente web o herramienta diferente cuando sea posible.

La prueba debe registrar versión, URL, capa y resultado.

21. Caso integrador

El grupo publica areas_verdes_publicas desde la vista creada en Semana 5.

Debe configurar:

  • Nombre estable;
  • Título y resumen;
  • Estilo por tipo;
  • Escalas de visibilidad;
  • CRS;
  • PNG con transparencia;
  • Consulta de atributos autorizados;
  • Acceso público según política.

Luego actualiza el metadato de Semana 6 con la URL WMS y verifica que el catálogo dirija correctamente al servicio.

Casos técnicos guiados — WMS con solicitudes reales

Los siguientes ejemplos utilizan una estructura típica de GeoServer. El dominio, workspace y nombres de capas deben reemplazarse por los del laboratorio.

Ejemplo 1 — GetCapabilities

http://localhost:8080/geoserver/municipio/wms?
service=WMS&
request=GetCapabilities&
version=1.3.0

En una URL real se escribe normalmente en una sola línea:

curl -o capabilities.xml \
  "http://localhost:8080/geoserver/municipio/wms?service=WMS&request=GetCapabilities&version=1.3.0"

El documento permite revisar:

  • Capas disponibles. Permite confirmar el nombre exacto (Name) que debe utilizarse en LAYERS y diferenciarlo del título legible para personas.
  • Estilos anunciados. Indica qué representaciones están disponibles y cuál puede utilizar el cliente en una petición GetMap.
  • CRS soportados. Permite formular la petición en un sistema realmente aceptado y anticipar posibles reproyecciones del servidor.
  • Formatos de imagen. Informa si el servicio puede responder PNG, JPEG u otras representaciones adecuadas al caso.
  • Operaciones. Permite comprobar si están disponibles GetMap, GetFeatureInfo y otras capacidades relevantes.
  • Límites o extensiones. Ayudan a construir un BBOX válido y a detectar solicitudes realizadas fuera de la cobertura del recurso.

Ejemplo 2 — GetMap completo

http://localhost:8080/geoserver/municipio/wms?
SERVICE=WMS&
VERSION=1.3.0&
REQUEST=GetMap&
LAYERS=municipio:areas_verdes&
STYLES=&
CRS=EPSG:3857&
BBOX=-7860000,-3975000,-7850000,-3965000&
WIDTH=1024&
HEIGHT=768&
FORMAT=image/png&
TRANSPARENT=true

Interpretación de parámetros

  • LAYERS. Identifica la capa publicada.
  • STYLES. Permite elegir una representación; vacío suele utilizar el estilo por defecto.
  • CRS. Define el sistema de referencia de la petición.
  • BBOX. Delimita el área solicitada.
  • WIDTH / HEIGHT. Determinan el tamaño de la imagen.
  • FORMAT. Define el tipo de representación.
  • TRANSPARENT. Es útil cuando la capa se superpone a otros mapas.

Ejemplo 3 — Relación entre BBOX y resolución

Si se solicita un BBOX de 10 km de ancho en 1.000 píxeles, cada píxel representa aproximadamente 10 metros. Si el mismo BBOX se solicita en 100 píxeles, cada píxel representa aproximadamente 100 metros.

Esto explica por qué escala, generalización, etiquetado y tamaño de respuesta están relacionados.

Ejemplo 4 — Orden de ejes en WMS 1.3.0

Un error frecuente aparece con EPSG:4326. WMS 1.3.0 utiliza el orden de ejes definido por el CRS; para EPSG:4326 esto puede implicar latitud/longitud, mientras CRS:84 utiliza longitud/latitud.

Por ello, una petición que intercambia ejes puede devolver un mapa vacío o de otra región. El estudiante debe verificar el CRS anunciado por el servidor y no copiar BBOX sin comprender su orden.

Ejemplo 5 — GetFeatureInfo

Después de renderizar un mapa, un cliente puede preguntar qué objeto existe bajo un píxel determinado. Un ejemplo genérico de GeoServer es:

http://localhost:8080/geoserver/municipio/wms?
SERVICE=WMS&
VERSION=1.3.0&
REQUEST=GetFeatureInfo&
LAYERS=municipio:areas_verdes&
QUERY_LAYERS=municipio:areas_verdes&
CRS=EPSG:3857&
BBOX=-7860000,-3975000,-7850000,-3965000&
WIDTH=1024&
HEIGHT=768&
I=512&
J=384&
INFO_FORMAT=application/json

I y J representan la posición consultada dentro de la imagen en WMS 1.3.0.

Ejemplo 6 — Estilo SLD mínimo

<?xml version="1.0" encoding="UTF-8"?>
<StyledLayerDescriptor version="1.0.0"
  xmlns="http://www.opengis.net/sld"
  xmlns:ogc="http://www.opengis.net/ogc">
  <NamedLayer>
    <Name>areas_verdes</Name>
    <UserStyle>
      <Title>Áreas verdes</Title>
      <FeatureTypeStyle>
        <Rule>
          <Name>areas_verdes_activas</Name>
          <PolygonSymbolizer>
            <Fill>
              <CssParameter name="fill">#7fbf7f</CssParameter>
            </Fill>
            <Stroke>
              <CssParameter name="stroke">#386b38</CssParameter>
              <CssParameter name="stroke-width">1</CssParameter>
            </Stroke>
          </PolygonSymbolizer>
        </Rule>
      </FeatureTypeStyle>
    </UserStyle>
  </NamedLayer>
</StyledLayerDescriptor>

El estilo muestra que WMS no entrega “el polígono verde” como dato; el servidor renderiza los objetos usando reglas cartográficas.

Ejemplo 7 — Escalas de visualización

Una capa de equipamientos puede mostrar símbolos desde 1:100.000, pero etiquetas solo desde 1:20.000. Esta estrategia reduce saturación y mejora rendimiento.

El estilo debería definirse considerando el uso y no solo estética.

Ejemplo 8 — Conectar desde QGIS

  1. Abrir Administrador de fuentes de datos → WMS/WMTS.
  2. Crear conexión a http://localhost:8080/geoserver/municipio/wms.
  3. Conectar y revisar la lista de capas.
  4. Cargar municipio:areas_verdes.
  5. Cambiar el CRS del proyecto y verificar reproyección.
  6. Consultar identificación si el servicio soporta GetFeatureInfo.

La prueba desde QGIS confirma interoperabilidad desde un cliente distinto al panel de administración de GeoServer.

Ejemplo 9 — Diagnóstico de una imagen vacía

Orden recomendado:

  1. revisar código HTTP;
  2. inspeccionar GetCapabilities;
  3. confirmar nombre exacto de capa;
  4. verificar CRS;
  5. comprobar BBOX y orden de ejes;
  6. revisar escala y reglas del estilo;
  7. probar una imagen pequeña en PNG;
  8. revisar logs del servidor.

Este procedimiento es más eficiente que cambiar parámetros al azar.

Referencia técnica: la documentación de GeoServer WMS incluye ejemplos de GetMap y GetFeatureInfo, mientras la especificación OGC WMS 1.3.0 define las operaciones estándar.

25. Preguntas de cierre

¿WMS entrega los objetos vectoriales originales?

No. Su función principal es entregar una representación cartográfica. Para acceso a objetos se utilizarán WFS u OGC API - Features.

¿Por qué GetCapabilities es importante?

Permite descubrir de manera interoperable operaciones, capas, estilos, formatos y CRS soportados.

¿Qué ocurre si la leyenda no coincide con el estilo?

El usuario puede interpretar incorrectamente el mapa. La consistencia de representación es parte de la calidad del servicio.

26. Errores frecuentes

  • “Si la capa se ve en GeoServer, el WMS funciona”. Debe probarse desde un cliente independiente.
  • “EPSG:4326 siempre usa el mismo orden de ejes en cualquier versión”. Debe revisarse la especificación y versión del servicio.
  • “GetFeatureInfo equivale a WFS”. Es una consulta asociada al mapa, no acceso completo a la colección.
  • “El estilo es solo decoración”. Influye en interpretación, legibilidad y rendimiento.

30. Síntesis

WMS desacopla la representación cartográfica de los clientes. La interoperabilidad no se demuestra activando un servicio, sino logrando que distintos clientes descubran capas, soliciten mapas, interpreten estilos y manejen errores de forma consistente.
