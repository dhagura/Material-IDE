Unidad 4 — Despliegue, administración y validación operativa

1. Marco de la semana

La semana final integra pruebas de interoperabilidad y consumo desde SIG de escritorio, aplicaciones web o móviles; documentación de arquitectura, administración, operación, usuario y API; entrega y defensa de una IDE mínima operativa con datos, catálogo, WMS, servicio de objetos o API, seguridad y evidencia de mantenimiento.

La evaluación sumativa del programa exige precisamente evidencia verificable del conjunto y dominio individual durante la defensa.

2. Propósito

La Semana 16 no debe convertirse en una presentación de diapositivas sobre lo que “debería” funcionar. La IDE debe demostrarse mediante casos de uso reales, clientes independientes y evidencias de operación.

El objetivo es cerrar la cadena completa construida durante el semestre:

Gobernanza → Datos → Metadatos → Catálogo → Servicios → Seguridad → Operación → Usuario

La defensa debe explicar decisiones y limitaciones, no únicamente mostrar resultados exitosos.

3. Resultados de aprendizaje

Al finalizar la asignatura, el estudiante deberá demostrar una IDE mínima operativa, probar interoperabilidad desde clientes distintos, entregar documentación suficiente para operación y mantenimiento, analizar riesgos/limitaciones y defender técnicamente sus decisiones.

También deberá demostrar dominio individual de conceptos y capacidad para diagnosticar un problema simple durante la defensa.

4. ¿Qué significa una IDE mínima operativa?

Para el proyecto del curso, una IDE mínima operativa debe articular como mínimo:

  • Alcance y gobernanza;
  • Base o recursos publicables;
  • Metadatos;
  • Catálogo;
  • WMS;
  • Servicio de objetos o API;
  • Control de acceso cuando corresponda;
  • Monitoreo;
  • Respaldo y recuperación;
  • Documentación;
  • Consumo desde clientes independientes.

“Mínima” significa que cubre el conjunto esencial de capacidades, no que pueda omitir calidad u operación.

5. Validación versus demostración

Una demostración muestra que algo funciona una vez. La validación verifica que cumple requisitos definidos.

Ejemplo

Mostrar un mapa en el navegador es una demostración. Confirmar que el WMS cumple el caso de uso, puede ser consumido desde QGIS, utiliza la capa correcta, tiene metadatos y mantiene acceso previsto es una validación más completa.

Por eso la defensa debe seguir la matriz de trazabilidad construida desde Semana 4.

6. Plan de pruebas final

El equipo debe preparar un plan que incluya:

  • Identificador de prueba;
  • Requisito asociado;
  • Precondición;
  • Pasos;
  • Resultado esperado;
  • Resultado obtenido;
  • Evidencia;
  • Estado.

Ejemplo

T-WMS-01: usuario público consume áreas verdes desde QGIS sin autenticación. El resultado esperado es que la capa se muestre y GetFeatureInfo solo exponga atributos autorizados.

7. Pruebas de descubrimiento

El usuario debe poder comenzar desde una necesidad y encontrar el recurso en catálogo.

Validar:

  • Búsqueda temática;
  • Vigencia del registro;
  • Responsable;
  • Licencia;
  • Enlace al servicio;
  • Relación con el dato correcto.

La prueba no debería utilizar un bookmark directo que evite el catálogo.

8. Pruebas WMS

Validar:

  • GetCapabilities;
  • GetMap;
  • Estilo;
  • CRS;
  • Leyenda;
  • Acceso;
  • Consumo en QGIS;
  • Consumo en cliente web cuando corresponda.

También debe probarse al menos un error controlado para demostrar capacidad de diagnóstico.

9. Pruebas de objetos/API

Validar:

  • Descubrimiento de colección;
  • Consulta de objetos;
  • Filtro o BBOX;
  • Paginación si aplica;
  • Formatos;
  • Permisos;
  • Atributos publicados.

La prueba debe comprobar que campos internos no aparecen si fueron excluidos por política.

10. Interoperabilidad entre clientes

El mismo servicio debe ser consumible desde más de un cliente apropiado.

Ejemplos:

  • QGIS;
  • Aplicación web;
  • Curl/navegador;
  • Script sencillo.

La prueba demuestra que el resultado no depende de una única aplicación propietaria o interfaz administrativa.

11. Pruebas de seguridad

Demostrar al menos:

  • Recurso público accesible;
  • Recurso restringido bloqueado sin autenticación;
  • Usuario autorizado accede;
  • Usuario no autorizado recibe rechazo;
  • Administración no está expuesta innecesariamente.

No es necesario realizar pruebas ofensivas avanzadas. El foco es verificar controles implementados.

12. Pruebas de monitoreo

Provocar una falla controlada o utilizar una simulación para demostrar que:

  • Se detecta la indisponibilidad;
  • Existe evidencia en logs;
  • Se genera la alerta o registro esperado;
  • El equipo puede identificar componente afectado.

Esto demuestra que la operación no depende únicamente de reportes de usuarios.

13. Prueba de recuperación

Seleccionar un componente y restaurarlo desde un respaldo.

Puede ser una base o configuración, siempre que se demuestre recuperación funcional posterior.

Registrar tiempo real y comparar con el RTO definido. Si no se cumple, no se oculta el resultado: se documenta como brecha y se propone mejora.

14. Documentación de arquitectura

Debe incluir:

  • Contexto;
  • Requisitos principales;
  • Arquitectura lógica;
  • Topología física;
  • Flujos de datos;
  • Componentes;
  • Dependencias;
  • Decisiones relevantes;
  • Riesgos y limitaciones.

El documento debe permitir a un nuevo integrante comprender el sistema sin reconstruirlo desde conversaciones informales.

15. Documentación de administración

Debe explicar tareas de administrador:

  • Cuentas y roles;
  • Despliegue;
  • Configuración;
  • Actualización;
  • Certificados;
  • Respaldo;
  • Monitoreo;
  • Recuperación.

No debe incluir secretos reales. Debe indicar cómo se obtienen de forma segura.

16. Documentación de operación

La documentación operacional se centra en tareas recurrentes y respuesta a incidentes.

Ejemplos:

  • Qué revisar ante WMS caído;
  • Cómo verificar espacio;
  • Cómo rotar logs;
  • Cómo restaurar;
  • Cómo escalar un incidente.

Un runbook operativo debe ser accionable y ordenado.

17. Documentación de usuario

Debe explicar cómo descubrir y consumir recursos sin exponer complejidad interna innecesaria.

Puede incluir:

  • Búsqueda en catálogo;
  • Conexión WMS en QGIS;
  • Uso de API;
  • Formatos;
  • Licencia;
  • Contacto;
  • Limitaciones conocidas.

La documentación de usuario debe probarse con alguien que no haya configurado la IDE.

18. Documentación de API

Una API debe informar:

  • Base URL;
  • Recursos;
  • Parámetros;
  • Formatos;
  • Autenticación;
  • Paginación;
  • Errores;
  • Ejemplos.

Cuando la implementación proporciona OpenAPI u otra descripción automática, puede utilizarse como base, pero debe complementarse con contexto y casos de uso.

19. Expediente de evidencia

El proyecto debe organizar evidencias para que la evaluación no dependa de una demostración en vivo que podría fallar por causas externas.

El expediente puede incluir:

  • Matrices;
  • Scripts;
  • URLs;
  • Exportaciones;
  • Capturas seleccionadas;
  • Logs;
  • Resultados de pruebas;
  • Respaldos de configuración;
  • Versiones de documentos.

La evidencia debe ser rastreable hacia requisitos.

20. Defensa técnica

La defensa no consiste en repartir secciones memorizadas. Cada integrante debe comprender la arquitectura completa y poder responder por sus decisiones.

Preguntas posibles:

  • ¿Por qué WMS y no descarga directa para este caso?;
  • ¿Quién es custodio?;
  • ¿Cómo se protege este dataset?;
  • ¿Qué ocurre si falla la base?;
  • ¿Cómo sabe un usuario si el dato está actualizado?;
  • ¿Qué cambiaría para escalar a diez veces la demanda?;
  • ¿Qué componente sustituiría si cambia el proveedor?

La calidad de la respuesta depende del razonamiento, no de recordar términos aislados.

21. Limitaciones y deuda técnica

Un proyecto académico no necesita resolver todo. Debe reconocer límites de manera profesional.

Ejemplo

“El monitoreo actual verifica disponibilidad cada minuto, pero no incluye trazas distribuidas. Para una operación a mayor escala se recomienda incorporar correlación avanzada”.

Documentar deuda técnica demuestra comprensión y evita presentar prototipos como soluciones perfectas.

22. Roadmap de evolución

La defensa puede cerrar con un roadmap priorizado:

  • Corto plazo: resolver brechas críticas;
  • Mediano plazo: automatizar despliegue y pruebas;
  • Largo plazo: federar catálogos, escalar infraestructura o incorporar nuevas APIs.

Cada mejora debe relacionarse con una necesidad, no con tendencias tecnológicas genéricas.

Caso técnico guiado — Validación final extremo a extremo

La defensa debe demostrar una cadena funcional completa. El siguiente guion puede utilizarse como base para la prueba final.

Ejemplo 1 — Recorrido de un recurso desde catálogo hasta cliente

  1. Buscar Áreas verdes en el catálogo.
  2. Abrir el metadato y verificar custodio, fecha, CRS y licencia.
  3. Seguir el enlace WMS.
  4. Cargar el servicio en QGIS.
  5. Mostrar la capa dentro del territorio esperado.
  6. Seguir el enlace OGC API - Features.
  7. Consultar 10 features dentro de un BBOX.
  8. Comparar un identificador entre API y base.
  9. Mostrar que el usuario público no puede acceder a un recurso restringido.
  10. Mostrar dashboard/logs de la operación.

Este recorrido demuestra que las piezas están conectadas y no son entregables independientes.

Ejemplo 2 — Script de smoke tests

#!/usr/bin/env bash
set -e

WMS="https://geo.ejemplo.cl/geoserver/municipio/wms"
API="https://geo.ejemplo.cl/api"

curl -fsS \
  "$WMS?service=WMS&request=GetCapabilities&version=1.3.0" \
  > /tmp/wms-capabilities.xml

curl -fsS \
  "$API/collections" \
  > /tmp/collections.json

curl -fsS \
  "$API/collections/areas_verdes/items?limit=1" \
  > /tmp/area.json

echo "Pruebas básicas completadas"

El script es deliberadamente simple. Puede ampliarse verificando códigos HTTP, contenido esperado o tiempo máximo.

Ejemplo 3 — Prueba negativa de autorización

curl -i https://geo.ejemplo.cl/api/collections/predios/items?limit=1

El usuario no autenticado debería recibir una respuesta coherente con la política de acceso. Luego se repite con un perfil autorizado.

La defensa debe explicar dónde se aplica el control y por qué.

Ejemplo 6 — Preguntas de defensa individual

El docente puede seleccionar aleatoriamente preguntas como:

  • ¿Por qué esta capa se publica como WMS y también como API?
  • ¿Qué ocurre si cambia el CRS de la fuente?
  • ¿Cómo sabe un usuario qué versión está usando?
  • ¿Dónde se define la licencia?
  • ¿Qué evidencia demuestra que el backup sirve?
  • ¿Por qué el usuario público recibe 403 en este recurso?
  • ¿Cómo identificaría una degradación de rendimiento?
  • ¿Qué componente reemplazaría primero si debiera migrar de proveedor?

La respuesta debe relacionar conceptos con la implementación concreta del equipo.

Ejemplo 7 — Incidencia durante la defensa

Una prueba de dominio individual puede introducir una falla controlada:

“La API responde 500, pero WMS continúa funcionando”.

El estudiante debería proponer una secuencia:

  1. confirmar alcance de la falla;
  2. revisar estado de API;
  3. consultar logs;
  4. comprobar conexión a DB;
  5. revisar cambios recientes;
  6. recuperar si corresponde;
  7. documentar incidente.

No se evalúa rapidez de adivinación, sino razonamiento y uso de evidencias.

Ejemplo 8 — Demostración desde dos clientes independientes

Una buena evidencia de interoperabilidad puede utilizar:

Cliente 1: QGIS
  → WMS
  → WFS u OGC API si el cliente lo soporta

Cliente 2: Navegador / curl / aplicación web
  → OGC API - Features
  → catálogo

El objetivo es demostrar que la infraestructura no depende de un único cliente propietario.

Criterio final de calidad

La defensa es satisfactoria cuando cada componente puede vincularse con una necesidad y existe evidencia de funcionamiento, seguridad, mantenimiento y limitaciones conocidas. Una IDE “bonita” pero imposible de recuperar, documentar o consumir desde otro cliente no cumple el resultado de aprendizaje completo.

23. Demostración sugerida

flowchart LR
    A["1. Usuario busca"] --> B["2. Revisa metadato"]
    B --> C["3. Consume WMS"]
    C --> D["4. Consulta API"]
    D --> E["5. Prueba acceso"]
    E --> F["6. Observa monitoreo"]

Este orden narra la IDE desde la perspectiva del usuario hacia la operación, evitando una demostración fragmentada por productos.

La organización exacta dependerá del número de grupos.

27. Preguntas de cierre

¿Qué diferencia existe entre que “funcione” y que esté validado?

La validación compara el comportamiento con requisitos y criterios de aceptación previamente definidos.

¿Por qué probar clientes independientes?

Porque demuestra interoperabilidad y reduce dependencia de una única herramienta.

¿Qué debe ocurrir si una prueba final falla?

Debe registrarse evidencia, analizar causa, decidir criticidad y documentar corrección o limitación. Ocultar la falla elimina aprendizaje y trazabilidad.

28. Errores frecuentes

  • “La defensa es una demo de interfaz”. Debe demostrar toda la infraestructura y decisiones.
  • “Si el proyecto académico tiene una limitación, significa que está mal”. Reconocer límites y proponer mitigación demuestra madurez.
  • “La documentación puede escribirse después sin probarla”. Debe verificarse con usuarios/administradores que no participaron en su redacción.

31. Síntesis final de la asignatura

La IDE final debe demostrar que gobernanza, datos, metadatos, catálogo, servicios, seguridad y operación forman una cadena coherente. El resultado más importante no es conocer una herramienta específica, sino ser capaz de diseñar, publicar, validar y mantener información geoespacial mediante principios de interoperabilidad y responsabilidad institucional.
